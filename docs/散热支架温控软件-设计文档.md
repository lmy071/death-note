## 1. 背景与目标

用软件把外置散热支架的开关交给温度决定：温度高就开，温度低就关，全程无人值守。

### 1.1 功能需求（原始）

- 每 5 分钟采样一次 CPU 温度与 GPU 温度，取两者较高值。
- 最高温度 > 70 ℃ → 打开"指定的 USB 接口"，给外置散热支架供电。
- 最高温度 < 70 ℃ → 关闭该 USB 接口，散热支架停止。

### 1.2 需求修订记录

| 原始需求 | 修订后 | 原因 |
| --- | --- | --- |
| 同时检测 CPU 和 GPU，取最高值 | **仅检测 GPU** | 本机 CPU 无可信温度源（§2.2 实测） |
| 超过 70 开，低于 70 关 | **≥72 开，≤68 关** | 单阈值会在 70 ℃ 附近反复开关（§5.2） |
| 开关指定 USB 接口的供电 | **通过米家控制 USB 模块** | 笔记本 USB 口不支持逐口断电（§2.1 实测） |

### 1.3 设计目标

1. **不会误动作**：读不到温度、读数异常、米家掉线，都不能让支架乱开乱关。
2. **不会失控**：程序崩溃或被杀掉后，支架必须回到安全状态（默认关闭）。
3. **可运维**：有日志、有托盘图标、有手动接管开关，出问题能查。
4. **低打扰**：常驻内存 < 30 MB，CPU 占用接近 0，不弹窗、不抢焦点。

## 2. 本机实测结论（设计依据）

> 以下全部为在本机实机运行得到的结果，不是推断。

### 2.1 USB 口无法软件断电 → 必须走米家

```
USB 主机控制器：Intel(R) USB 3.20 可扩展主机控制器 - 1.20 (Microsoft)
               PCI\VEN_8086&DEV_7A60&SUBSYS_03531558&REV_11
```

全部 USB 设备（含外接 Genesys Logic `05E3:0610` / `0626` 集线器）都挂在这**唯一一个**控制器下，共享同一条 5V VBUS 供电轨。笔记本的 USB 端口**不支持 per-port power switching**，`IOCTL_USB_HUB_SET_PORT_FEATURE` 之类调用必然失败。

**结论**：不碰 USB 供电，改为控制已接入米家的 USB 模块 —— 由模块本身负责通断支架供电。

### 2.2 CPU 温度在本机完全不可用 → 放弃 CPU

实测排查了所有 Windows 侧途径，全部失败：

| 途径 | 实测结果 |
| --- | --- |
| `MSAcpi_ThermalZoneTemperature` | 只有 **1 个**热区 `ACPI\ThermalZone\TZ0__0` |
| `Win32_PerfFormattedData_Counters_ThermalZoneInformation` | 同一个 `\_TZ.TZ0`，值 3482（与上者同源） |
| `Win32_TemperatureProbe` | **空结果**（0 个实例） |
| `root\WMI` 全部 1585 个类 | 无任何 CPU/GPU 温度类；仅有 `KernelThermalConstraintChange` 等策略类 |
| OEM 命名空间（`root\IntelDTT` / `root\DTT`） | **均不存在** |
| `root\Intel_ME` | 仅 AMT/OOB 管理类，无温度 |

**决定性证据 —— 满载不变化：**

```
施加 20 线程满载 120 秒，每 5 秒采样一次：
   2.0s  TZ0=75.1C  GPU=53C
  13.6s  TZ0=75.1C  GPU=57C
  42.5s  TZ0=75.1C  GPU=61C
  71.3s  TZ0=75.1C  GPU=62C
 117.3s  TZ0=75.1C  GPU=63C     ← CPU 满载 2 分钟，TZ0 全程恒定
停止负载后：TZ0 = 75.1C        ← 依然不变
```

CPU 满载两分钟，TZ0 **一次都没有变动**（75.1 ℃ 恒定）；同时间 GPU 从 52 ℃ 稳步升到 63 ℃。

这是 ACPI 固件暴露的**机壳/主板热区**，既不刷新、也不代表 CPU 核心温度（DTS）。拿它做 70 ℃ 判断等于用假数据决策 —— 支架会永远保持同一个状态。

**结论：采纳 D1，彻底放弃 CPU 温度，只依赖 GPU。**

### 2.3 GPU 温度可信，但有字段陷阱

```
nvidia-smi --query-gpu=name,temperature.gpu,utilization.gpu,power.draw --format=csv
name, temperature.gpu, utilization.gpu [%], power.draw [W]
NVIDIA GeForce RTX 4060 Laptop GPU, 52, 0 %, 590.01 W    ← power.draw 明显错误
```

`temperature.gpu` 读数合理且随负载单调变化（52→63 ℃），可信。
但 `power.draw` 返回 **590.01 W**（RTX 4060 Laptop 的 TGP 上限是 115 W），说明该字段在此驱动/混合显卡环境下返回垃圾值。

**结论：只解析 `temperature.gpu` 单个字段**，其余字段一律不参与决策，也不写入日志（避免误导排障）。

### 2.4 网络环境：FlClash TUN 会干扰局域网发现

```
路由表：0.0.0.0/0 → 28.0.0.2 (FlClash Meta Tunnel)  [metric 0]
      0.0.0.0/0 → 192.168.0.1 (以太网 3)           [metric 0]
进程：FlClash / FlClashCore / FlClashHelperService 均在运行
```

实测影响：

- `Resolve-DnsName api.io.mi.com` 返回 **28.0.0.13 / 28.0.0.9**（FlClash 虚拟 IP，非真实 DNS）
- 对本网段 254 个地址做 TCP 端口扫描时，**几乎全部"端口开放"** —— 这是 TUN 模式伪造接受连接造成的假阳性
- 真实 ARP 表中本网段只有 3 台设备（`192.168.0.1` 网关、`.101`、`.102`）
- 对 `.101` / `.102` 做 MiIO 握手（UDP 54321）**无响应**，说明当前在线设备不是米家设备
- 米家云 API `https://api.io.mi.com/app/...` 经代理访问返回 **401**（可达，需鉴权），不是超时

**结论（对实现的两条硬约束）：**

1. **局域网自动发现不可靠**，本方案**不依赖局域网发现**，全部走米家云 API。
2. **程序必须显式处理代理**：默认读取系统代理；若走 TUN 导致直连异常，需支持"强制直连"配置项。云 API 请求必须绕开 TUN 的虚假解析，使用固定域名 + 系统代理。

### 3.1 分层职责

| 层 | 职责 | 明确不做 |
| --- | --- | --- |
| 调度器 | 每 5 分钟触发采样；睡眠唤醒后补采并重排定时 | 不做温度判断 |
| GPU 采样器 | 调 `nvidia-smi`，超时/重试/合理性校验，输出带可信度的样本 | 不知道米家存在 |
| 决策状态机 | 纯函数 `(样本, 当前状态, 历史) → 新状态 + 动作` | 不读硬件、不写网络 |
| 执行器 | 把"开/关"翻译成米家 MIoT 调用，幂等、带重试与回读校验 | 不做温度判断 |
| 托盘 UI | 显示温度、支架状态、下次采样倒计时；手动接管 | 不做决策 |

**决策状态机必须是纯函数**，这是整个设计里最关键的一条约束：它让 72/68 迟滞逻辑可以在没有 GPU、没有米家账号的情况下被完整单元测试，也方便日后调整阈值而不用碰任何 IO 代码。

## 4. GPU 采样设计

### 4.1 采集方式

| 优先级 | 方式 | 超时 | 重试 |
| --- | --- | --- | --- |
| 主 | `nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader,nounits` | 3 s | 1 次 |
| 备 | NVML 动态加载（`nvml.dll`，随 NVIDIA 驱动安装）`nvmlDeviceGetTemperature` | 1 s | — |

> 实现建议：优先 NVML（进程内调用，无子进程创建开销）；`nvidia-smi` 作为对照实现与兜底，便于验证 NVML 是否可用。

### 4.2 读数可信度校验

样本结构：

```
Sample {
    Timestamp
    TemperatureC   : double
    Confidence     : Valid | Invalid | Stale
    Source         : Nvml | NvidiaSmi | None
}
```

校验规则：

| 规则 | 判定 |
| --- | --- |
| 返回能解析为整数且落在 `[-10, 120]` | `Valid` |
| 返回 `N/A`、空、非数字、负值超出范围 | `Invalid` |
| `nvidia-smi` 退出码非 0 或超时 | `Invalid` |
| 连续 3 次采样（15 分钟）数值完全不变（±0.1 ℃） | `Stale` |

`Stale` 规则用于识别"驱动挂死但仍返回旧值"的退化情形。真实 GPU 温度在 15 分钟内不会一动不动（实测空闲时也有 ±1 ℃ 波动）。

### 4.3 无效样本的处理

| 情况 | 决策行为 |
| --- | --- |
| 样本 `Valid` | 正常参与 72/68 判断 |
| 样本 `Invalid` / `Stale` | **保持当前支架状态不变**，记 WARN，托盘图标变黄 |
| 连续无效累计 > 30 分钟 | **强制关闭支架**，托盘图标变红 |

> 为什么"失联时保持现状"而不是"立刻关"：支架掉电会让机器更热，短暂抖动就断电反而有害。但长时间失联说明软件已失去判断能力，此时断电止损（关闭是安全方向）。

## 5. 决策状态机（核心逻辑）

### 5.1 为什么不用原始的单阈值

原始需求"超过 70 开、低于 70 关"是单阈值开关，在真实硬件上有两个必然踩的坑：

1. **抖动**：温度在 70.0 附近波动（69.8 → 70.2 → 69.9），支架在几分钟内反复开关。继电器和风扇频繁启停显著缩短寿命，噪音也难受。
2. **边界歧义**：`恰好 70.0` 属于"超过"还是"低于"？需求没定义。

### 5.2 采用方案：双阈值迟滞 + 连续确认 + 最小保持时间

```
               GPU 温度 ≥ 72 ℃ 且连续 2 次采样
     OFF  ────────────────────────────────▶  ON
      ▲                                       │
      └───────────────────────────────────────┘
               GPU 温度 ≤ 68 ℃ 且连续 2 次采样
               且已保持 ON 至少 10 分钟
```

| 参数 | 默认值 | 可配置 | 说明 |
| --- | --- | --- | --- |
| `OnThresholdC` | 72 | 是 | 高于等于此值开启 |
| `OffThresholdC` | 68 | 是 | 低于等于此值关闭 |
| `ConfirmSamples` | 2 | 是 | 连续 N 次满足才动作（5 分钟一次 = 10 分钟确认） |
| `MinOnDuration` | 10 min | 是 | 开启后至少保持，避免短循环 |
| `MinOffDuration` | 5 min | 是 | 关闭后至少保持 |
| `FailSafeCloseAfter` | 30 min | 是 | 连续无效多久后强制关闭 |

**为什么是 72/68**：留出 4 ℃ 死区，配合"连续 2 次确认"，把抖动引起的开关次数压到接近 0；相对 70 ℃ 中位值仅偏移 ±2 ℃，仍符合"超过 70 就加强散热"的原始意图。

### 5.3 状态机定义

状态：`Off` / `On` / `Failsafe`

```
每 5 分钟:
  sample = GpuSampler.Collect()

  if sample.Confidence == Valid:
      missStreak = 0
      hotStreak  = (sample.TemperatureC >= OnThresholdC)  ? hotStreak+1  : 0
      coldStreak = (sample.TemperatureC <= OffThresholdC) ? coldStreak+1 : 0

      switch state:
        Off: if hotStreak  >= ConfirmSamples and offElapsed >= MinOffDuration → 动作 On,  state = On
        On : if coldStreak >= ConfirmSamples and onElapsed  >= MinOnDuration  → 动作 Off, state = Off
        Failsafe: if hotStreak >= ConfirmSamples → 动作 On, state = On
                  else if coldStreak >= ConfirmSamples → state = Off（不动作）

  else:
      missStreak += 1
      if missStreak * Interval >= FailSafeCloseAfter:
          动作 Off, state = Failsafe
```

关键性质：

- **幂等**：重复输入同一样本不产生额外动作；动作执行前先回读执行器状态，已是目标状态则跳过。
- **无副作用**：状态机不读硬件、不发网络请求，只返回 `Action` 枚举（`None` / `TurnOn` / `TurnOff`）。

## 6. 执行器设计：米家接口

### 6.1 米家接入的三条路径

| 路径 | 做法 | 可行性 | 适用 |
| --- | --- | --- | --- |
| **A. 米家云 API**（推荐） | 模拟米家 App 登录，调 `api.io.mi.com/app/miotspec/prop/set` | ★★★★★ 实测可达（401 而非超时），无需额外组件 | 任意网络环境，模块在任意子网 |
| B. 局域网本地直连（MiIO） | UDP 54321 + Token，AES 加密直连模块 | ★★☆☆☆ 需先拿到 Token；受 TUN/AP 隔离影响 | 仅当云 API 不可用 |
| C. 米家开放平台（iot.mi.com） | 官方 OAuth 云对接 | ☆☆☆☆☆ 个人开发者无权限，需企业资质 | 不适用 |

**采纳 A（云 API）**，B 作为可选降级，C 排除。

### 6.2 云 API 协议细节（实测/源码核对）

请求结构（来自 MiService 开源实现，已在 `api.io.mi.com` 上实测确认端点可达）：

```
POST https://api.io.mi.com/app/miotspec/prop/set
Header: User-Agent: <MiIO UA>
Header: x-xiaomi-protocal-flag-cli: PROTOCAL-HTTP2
Body  : { _nonce, data, signature }
```

**签名算法**（`sign_data`）：

```
nonce      = base64( random(8 字节) || uint32(unixTime / 60) )
snonce     = base64( sha256( base64decode(ssecurity) || base64decode(nonce) ) )
msg        = uri + "&" + snonce + "&" + nonce + "&data=" + jsonData
signature  = base64( HMAC-SHA256( key = base64decode(snonce), msg ) )
```

**属性设置**（`prop/set`）：

```json
{
  "params": [
    { "did": "<设备DID>", "siid": <服务ID>, "piid": <属性ID>, "value": <on|off 或 true|false> }
  ]
}
```

**属性读取**（`prop/get`）—— 用于回读校验：

```json
{
  "params": [
    { "did": "<设备DID>", "siid": <服务ID>, "piid": <属性ID> }
  ]
}
```

**登录链路**：`https://account.xiaomi.com/pass/serviceLogin?sid=xiaomiio` 获取 `_sign` → 提交账号密码 → 获取 `ssecurity` 与 `xiaomiio` 服务令牌 → 令牌持久化到本地，后续请求复用。

> 登录涉及 OTP 两步验证与 `Domain=.xiaomi.com` 的 Cookie 处理，在 .NET Framework 的 `HttpWebRequest` 下有兼容性问题（实测报"Cookie 的 Domain 部分无效"）。**实现时必须用 `HttpClient` + 手动 CookieContainer 配置，或自行解析 Set-Cookie**，不能用默认的 Cookie 解析器。

### 6.3 米家模块的 siid/piid 定位

不同 USB 模块的 MIoT 结构不同，**不能写死**。实现要求：

1. 首次配置时调用 `miotspec/spec` 拉取该型号的能力描述（也可查 `home.miot-spec.com`）。
2. 从 spec 中定位"开关"服务：通常是 `siid=2, piid=1`，类型 `bool`，描述含"开关/on/switch"。
3. 若模块是插座形态，可能是 `siid=2, piid=1`（开关）或 `siid=3, piid=2`（功率）。
4. 配置项允许用户直接填写 `siid` / `piid` / 开值 / 关值，避免猜错。

**开/关值的形态**：多数设备接受 `true/false`，部分老设备只接受 `"on"/"off"`。配置中提供 `onValue` / `offValue` 两种形态，默认 `true/false`，失败时自动尝试另一种。

### 6.4 IActuator 接口

```csharp
public enum PowerState { Unknown, Off, On }

public interface IActuator
{
    string Name { get; }
    Task<bool> IsAvailableAsync(CancellationToken ct);        // 云端/设备是否可达
    Task<PowerState> ReadAsync(CancellationToken ct);          // 回读真实状态
    Task ApplyAsync(PowerState target, CancellationToken ct);  // 幂等下发
}
```

实现约束：

- `ApplyAsync` **必须幂等**：重复下发同一目标不产生副作用。
- 每次下发后**回读校验**（`prop/get`），不一致则重试（最多 3 次，退避 1s / 2s / 4s），仍失败记 ERROR 并进入 `Failsafe`。
- 执行器内部维护**串行队列**，杜绝并发下发。
- 网络请求总超时 15 s（云 API 在代理下可能较慢），超时视为失败但**不重试轰炸**。

### 6.5 三个实现

| 实现 | 通信 | 用途 |
| --- | --- | --- |
| `SimulatedActuator` | 无，只写日志 | **开发/测试默认**，先把逻辑跑通 |
| `MiHomeCloudActuator` | 米家云 API（HTTPS） | 生产默认 |
| `MiHomeLocalActuator` | 局域网 MiIO（UDP + AES） | 云 API 不可用时的降级（需 Token） |

### 6.6 凭据与安全

- 小米账号密码**不落盘**，仅保存 `ssecurity` + 服务令牌（有效期较长），存于 `%ProgramData%\TempFanCtl\session.dat`。
- `session.dat` 用 DPAPI（`ProtectedData`，CurrentUser 范围）加密，防止明文泄露。
- 令牌过期时触发重新登录；登录失败不阻塞主循环，托盘提示"需要重新登录米家"。
- 日志中**禁止输出** token、ssecurity、password、完整 `did`（`did` 脱敏为前 4 位 + `****`）。

## 7. 运行时设计

### 7.1 定时

- 主循环用 `PeriodicTimer`（5 分钟）而非 `Thread.Sleep`，避免累积漂移。
- **睡眠/唤醒**：注册 `SystemEvents.PowerModeChanged`，唤醒后立刻补采一次（睡眠期间机器可能已过热），然后重置计时。
- 记录每次实际采样时间戳；两次间隔偏差 > 30 s 记 WARN。

### 7.2 进程形态

| 项 | 设计 |
| --- | --- |
| 形态 | 托盘常驻（`NotifyIcon`），无主窗口；双击打开状态面板 |
| 开机自启 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（无需管理员） |
| 单实例 | 命名 Mutex `Global\TempFanCtl`，第二个实例唤起第一个的托盘窗口 |
| 权限 | **普通用户即可**（不走驱动、不碰 USB 供电，无需管理员） |
| 崩溃恢复 | 可选注册"失败即重启"计划任务；至少保证崩溃时支架已关闭 |

## 8. 技术选型与工程结构

### 8.1 语言与运行时

本机**未安装 .NET SDK**，但自带 .NET Framework 4.8（`Release = 533320`）与 `csc.exe`（4.8.9232.0）。因此：

| 选项 | 说明 | 结论 |
| --- | --- | --- |
| **C# / .NET Framework 4.8，`csc.exe` 直接编译** | 零额外依赖，本机可立即构建；WinForms 托盘原生支持 | ✅ 首选 |
| C# / .NET 8 + 自包含单文件 | 需联网装 SDK，产物 ~70 MB | 仅当需跨机器分发 |
| C++ / Win32 | 体积最小（< 1 MB），但托盘/JSON/HTTPS 都要手写 | 不推荐 |
| Python + PyInstaller | 体积大，杀软误报率高，常驻内存偏高 | 不推荐 |

**推荐：C# + .NET Framework 4.8，单文件 `TempFanCtl.exe`（约 200 KB）**，Win11 开箱即用。

> 注意：本机 `python` 是 WindowsApps 占位存根（执行无输出），**不能依赖 Python**。米家协议必须用 C# 自行实现（签名算法已在 §6.2 给出，纯 `System.Security.Cryptography` 即可完成）。

## 12. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 米家云 API 为非官方接口，可能变更 | 控制失效 | 抽象为 `IActuator`，可切局域网 MiIO；协议变更只改 `MiHomeCloudActuator` |
| 账号令牌过期 / 异地登录 | 控制失效 | 自动重登 + 托盘告警；失败不阻塞主循环 |
| 米家云响应慢（经代理） | 开关延迟 | 超时 15 s；`MinOnDuration` 保证不会因延迟反复动作 |
| TUN 代理导致云 API 异常 | 请求失败 | 提供 `forceDirect` 配置；失败重试 3 次后告警 |
| 模块离线（Wi-Fi 掉线） | 控制失效 | `IsAvailable=false` 时不轰炸重试，托盘变黄；恢复后自动同步状态 |
| GPU 驱动挂死返回旧值 | 决策基于假数据 | `Stale` 判定（连续 3 次不变） |
| 阈值抖动 | 频繁开关 | 72/68 迟滞 + 连续 2 次确认 + 最小保持时间 |
| 程序崩溃时支架处于 ON | 支架常开 | `try/finally` + `ProcessExit` 兜底关闭；重启后首次采样前保持 OFF |
