## 一、核心性能指标

### LCP（最大内容绘制）

- 视图中最大图像/文本块的呈现时间
- 良好标准：**≤ 2.5s**
- 监测到滚动/输入事件时停止搜索，取最后一个最大内容
- 通过 `PerformanceObserver` 监听 `largest-contentful-paint`

### FCP（首次内容绘制）

- 任何内容首次在屏幕上呈现的时间
- 良好标准：**≤ 1s**
- 与 FP（First Paint）类似，但 FP 仅表示第一个像素绘制时间

### FID（首次输入延迟）→ 已被 INP 取代

- 用户首次交互到浏览器开始处理事件的时间
- 良好标准：**≤ 100ms**
- 2024年3月已被 **INP** 取代

### INP（交互到下一次绘制）

- 观察页面生命周期内所有点击、触摸、键盘交互的延迟
- 比 FID 更全面，考虑所有交互而非仅首次
- 仅受鼠标点击、触摸、键盘按键影响

### CLS（累积布局偏移）

- 衡量页面整个生命周期内最大意外布局偏移
- 仅计算已有可见元素非预期的位置变化；新增元素若导致已有内容移位也会被计入
- 良好标准：**≤ 0.1**

### Long Task（长任务）

- 阻塞主线程超过 **50ms** 的任务
- 虽非 Web Vitals 指标，但对体验影响大
- 原因：长事件处理、昂贵回流/DOM操作、长循环

## 二、优化措施

### 2.1 代码分割 & 懒加载

**代码分割**：减小初始 JS 体积，按路由/功能拆分按需加载

**懒加载**：推迟非关键组件/资源的加载

```jsx
const DownloadFile = lazy(() => import('./page/OperateFile'));
const TimeSelect = lazy(() => import('./page/TimeSelect'));
```

### 2.2 HTTP 缓存策略

| 资源类型 | Cache-Control | 补充 |
| --- | --- | --- |
| HTML | `no-cache` 或 `max-age=0, must-revalidate` | 每次验证是否最新 |
| 静态资源(JS/CSS) | `public, immutable, max-age=31536000` | 文件名含 hash（cache-busting） |
| 其他(图片/API) | `no-cache`  • ETag/Last-Modified | 条件请求，304复用 |

**关键概念**：

- `immutable` — 资源在 hash 变化前不更新，阻止重新验证
- `ETag` / `Last-Modified` — 支持条件请求，未变化返回 304
- 含 `Authorization` 的请求默认为 private 数据

### 2.3 CDN

- 分布式服务器网络，缓存源站资源
- 更接近用户 → 降低 RTT
- 支持 HTTP/2、HTTP/3、缓存和压缩

### 2.4 代码最小化

| 类型 | 工具/方案 |
| --- | --- |
| JavaScript | Terser — Tree Shaking + 缩短变量名 + 删空格 |
| CSS | mini-css-extract-plugin — 提取独立CSS文件，支持按需加载 |
| 图片 | WebP 替代 JPEG/PNG（体积减少25%-35%），CDN图片优化（节省40%-80%） |

WebP 兼容方案：

```html
<picture>
  <source type="image/webp" srcset="flower.webp">
  <source type="image/jpeg" srcset="flower.jpg">
  <img src="flower.jpg" alt="">
</picture>
```

### 2.5 HTTP 协议与捆绑优化

| 版本 | 特点 |
| --- | --- |
| HTTP/1.0 | 每次请求建立独立TCP连接 |
| HTTP/1.1 | 持久连接，管线化 |
| HTTP/2.0 | 多路复用、Server Push、头部压缩 |
| HTTP/3 | QUIC协议，更低延迟，更灵活流控 |

**关键结论**：

- HTTP/1.x 时代的资源内联、雪碧图等捆绑优化，在 HTTP/2 多路复用下不再必要
- Chrome 已不支持 HTTP/2 Server Push
- HTTP/3 对开发者几乎无感知变化，协议层自动优化

## 三、渲染优化

### 3.1 渲染阻塞资源

- CSS 和 JS 会阻塞渲染
- blocking=render 属性可标记为渲染阻塞资源（HTML 标准已支持）
- 优化关键资源加载顺序以提升 FCP/LCP

### 3.2 Browser Resource Hints

| 提示 | 用途 | 优先级 |
| --- | --- | --- |
| `prefetch` | 预缓存未来可能需要的资源 | 低 |
| `dns-prefetch` | 预解析DNS | 低 |
| `preconnect` | 预建立连接（DNS+TLS+TCP） | 中 |
| `prerender` | 预渲染整个页面 | 高 |
| `preload` | 尽快下载重要资源 | 高 |

建议 `dns-prefetch` + `preconnect` 配合使用，避免过度配置。

### 3.3 Script 加载策略

- `async` — 异步加载，加载完立即执行
- `defer` — 异步加载，HTML解析完后按顺序执行
- `type="module"` — 自动延迟执行

### 3.4 Fetch Priority API

`fetchpriority` 属性可用于 `<link>`、`<img>`、`<script>`：

- `high` — 高优先级
- `low` — 低优先级
- `auto` — 浏览器决定（默认）

## 四、图片优化

### 4.1 图片属性

| 属性 | 值 | 说明 |
| --- | --- | --- |
| `loading` | `eager` / `lazy` | 立即加载 / 视口内才加载 |
| `fetchpriority` | `high` / `low` / `auto` | 加载优先级 |
| `width`  • `height` | 固定尺寸 | 避免CLS布局偏移 |
| `decoding` | `sync` / `async` / `auto` | 同步/异步解码 |

关键图片预加载：

```html
<link rel="preload" fetchpriority="high" as="image" href="hero.webp" type="image/webp">
```

响应式图片：

```html
<img src="flower-large.jpg" srcset="small.jpg 480w, large.jpg 1080w" sizes="50vw">
```

避免 CLS 的 CSS 方案：

```css
img {
  aspect-ratio: 16 / 9;
  width: 100%;
  object-fit: cover;
}
```

### 4.2 图片格式选择

| 格式 | 适用场景 | 特点 |
| --- | --- | --- |
| JPEG | 摄影图片 | 有损压缩，体积小 |
| SVG | Logo/Icon | 矢量，无限缩放 |
| PNG | 高清图/透明 | 无损，WebP更优 |
| WebP | 通用替代 | 体积更小，兼容性好 |
| Video | 动画 | 远小于GIF，无颜色限制 |

## 五、视频优化

### 5.1 Preload 属性

- `none` — 不预加载
- `metadata` — 仅获取元数据（**推荐默认值**）
- `auto` — 预加载整个视频

### 5.2 用 Video 替代 GIF

- 同等视觉质量下，视频文件远小于 GIF
- 懒加载 + IntersectionObserver 自动播放：

```html
<video autoplay muted loop playsinline poster="placeholder.jpg">
  <source src="anim.webm" type="video/webm">
  <source src="anim.mp4" type="video/mp4">
</video>
```

- LCP 场景可预加载 poster 图片：

```html
<link rel="preload" as="image" href="poster.jpg" fetchpriority="high">
```

## 六、预渲染

### SSR（服务端渲染）

- 服务器执行应用逻辑，生成完整 HTML
- 优势：首屏快、SEO 好
- 代价：服务器处理时间，每次请求重新生成
- 权衡合理：服务器时间可控，用户网络/设备不可控

### SSG（静态站点生成）

- 构建时编译，生成静态文件
- 适合所有用户内容相同的场景（博客、文档站）
- 静态文件可缓存到 CDN，零运行时开销

## 七、JS 执行优化

### 7.1 requestAnimationFrame

- UI 改动推荐使用，比 `setTimeout`/`setInterval` 更智能
- 确保回调在下次重绘前执行，避免丢帧

### 7.2 避免长任务

| 方法 | 说明 |
| --- | --- |
| **Web Workers** | 后台线程执行计算密集任务，通过 postMessage 通信，不能操作DOM |
| **任务拆分** | 长任务拆成小异步子任务，通过 `yieldToMain()` 释放主线程 |
| **scheduler.postTask** | 细粒度任务调度，指定优先级（浏览器支持有限） |
| **scheduler.yield** | 释放主线程机制 |
| **requestIdleCallback** | 空闲时执行低优先级任务 |

⚠️ **微任务不会释放主线程**：Promise 微任务在当前任务结束后立即执行，主线程保持繁忙。

### 7.3 yieldToMain 模式

```jsx
const TASK_DEADLINE = 50 // ms
let deadline = performance.now() + TASK_DEADLINE

function yieldToMain() {
  return new Promise((resolve) => setTimeout(resolve, 0))
}

function otherTask() {
  // 执行一小块工作...
}

while (tasks.length > 0) {
  if (navigator.scheduling?.isInputPending() || performance.now() >= deadline) {
    await yieldToMain()
    deadline = performance.now() + TASK_DEADLINE
    continue
  }
  otherTask()
}
```

### 7.4 批处理

- React 虚拟DOM = 批处理策略：所有变化应用在虚拟DOM，一次性提交重绘
- 减少实际DOM操作和浏览器重绘次数

## 八、总结

前端性能优化是持续过程，核心思路：

1. **测量先行** — Lighthouse / PerformanceObserver / WebPageTest
2. **指标驱动** — LCP、FCP、INP、CLS 四大核心指标
3. **分层优化** — 网络层(缓存/CDN) → 资源层(压缩/格式) → 渲染层(阻塞/预加载) → 执行层(长任务/批处理)
4. **持续监控** — 不是一次性工作，需要持续关注改进
