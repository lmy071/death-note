# 2026-08-31｜Vue 3 离线优先数据一致性架构

## 题目

你负责设计一个大型企业级 Vue 3 应用。该应用需要支持弱网和离线工作：用户可以在多个浏览器标签页甚至多台设备上编辑同一批业务实体；离线期间允许新增、修改、删除，恢复网络后自动同步。系统还要求支持乐观 UI、撤销、审计日志，并保证关键业务字段不能被静默覆盖。

请设计一套**离线优先的数据一致性架构**。重点说明：本地状态与服务端状态的边界、IndexedDB 持久化模型、Mutation Queue、幂等性、冲突检测与解决、版本协议、多标签页并发、Vue 3 响应式状态组织、同步失败恢复、Schema 演进，以及如何观测同步系统是否正在发生数据丢失或冲突异常。

## 背景 / 场景

系统包含数十个业务模块，部分用户会连续离线数小时。一次离线期间可能产生数千次 mutation。应用采用 Vue 3 + TypeScript，允许长期保持页面不刷新，并支持灰度发布，因此同一时刻可能存在不同前端版本产生的数据操作。

要求：

- 用户操作必须立即反馈，不能等待服务端确认后才更新 UI。
- 网络恢复后不能简单采用“最后写入者获胜”覆盖关键字段。
- 同一个 mutation 因重试而发送多次时，服务端不能重复执行。
- 页面刷新、浏览器崩溃后，未同步操作必须能够恢复。
- 多标签页不能同时无序消费同一份同步队列。
- 前端升级不能让旧版本持久化数据导致新版本启动失败。

## 核心考察点

- 是否能区分 **Server State、Local Durable State、Ephemeral UI State**，而不是把所有状态都塞进 Pinia。
- IndexedDB 中是否采用实体快照、Mutation Log / Outbox、同步游标等可恢复的数据模型。
- mutation 是否具有稳定的 `operationId`、实体版本和客户端版本，使重试具备幂等语义。
- 是否理解乐观并发控制：ETag / version、compare-and-swap、baseVersion，而不是仅依赖时间戳。
- 能否根据业务语义选择冲突策略：自动 merge、字段级 merge、CRDT、服务端裁决或人工解决，而不是全局 LWW。
- 多标签页下是否考虑 BroadcastChannel + Leader Election / Lease，避免重复同步和脑裂。
- Vue 3 响应式层是否与持久化层解耦，避免把 IndexedDB 当成 Pinia 的透明序列化。
- 是否考虑 poison mutation、指数退避、Dead Letter、队列压缩、依赖排序与批量提交。
- Schema migration 是否支持版本化、向前/向后兼容以及失败回滚。
- 是否建立 pending mutation、冲突率、同步延迟、重试次数、DLQ、数据校验失败等可观测指标。

## 追问方向

1. 用户离线修改实体 A 三次，是否应该向服务端发送三次 mutation？什么时候允许进行 mutation compaction？
2. 两台设备都基于 `version=12` 修改同一个关键字段，第二个请求应该如何处理？为什么不能直接使用客户端时间戳决定胜负？
3. 如果一次操作是“账户余额 +100”，为什么 `SET balance=xxx` 和 `INCREMENT 100` 的冲突语义完全不同？
4. 多标签页使用 Leader Election 后，如果 Leader 被浏览器冻结但没有真正退出，如何防止旧 Leader 恢复后继续写入形成脑裂？
5. 一个 mutation 依赖前一个离线创建操作返回的服务端 ID，队列如何表达依赖关系？
6. 新版本把实体 Schema 从 v4 升级到 v5，但用户 IndexedDB 中还有 v3 的未同步 mutation，升级流程如何设计？
7. 什么业务场景值得采用 CRDT？什么情况下 CRDT 反而会显著增加系统复杂度？
8. 如何证明系统“没有静默丢数据”，而不是仅监控接口成功率？

## 参考答案要点

### 1. 状态分层

将状态至少拆为三层：服务端权威状态、本地可持久化的离线工作集、纯 UI 临时状态。Pinia 更适合作为 UI 与领域视图模型层；IndexedDB 是 durable storage。二者通过 Repository / Data Access Layer 同步，不应直接把整个 Pinia Store 自动持久化。

### 2. Local Outbox / Mutation Log

每次业务写操作先生成稳定的 `operationId`，以事务方式同时更新本地实体视图和 Outbox。只有两者都提交成功，UI 才认为本地操作成功。这样即使页面崩溃，Outbox 仍可以恢复并继续同步。

Mutation 至少包含：`operationId`、entityId、operationType、payload、baseVersion、schemaVersion、clientVersion、createdAt、dependencyIds 与 retry metadata。

### 3. 幂等与 Exactly-once 幻觉

浏览器到服务端的网络无法可靠提供 exactly-once delivery。架构应接受 at-least-once delivery，通过 `operationId` + 服务端幂等表 / 去重窗口，使重复请求产生与一次执行相同的业务结果。

### 4. 冲突检测

实体更新携带 `baseVersion`。服务端只有在当前版本仍等于 baseVersion 时才直接提交，否则返回结构化 conflict。客户端或服务端再根据字段和业务规则进行 merge。关键字段必须显式冲突，不允许静默 LWW。

### 5. 冲突解决不是一种算法

文本协作等高并发可考虑 CRDT / OT；普通表单可采用字段级 optimistic concurrency；金融、审批等强业务约束应由服务端领域逻辑裁决；无法自动解决时应保留双方版本并让用户选择。架构应允许不同 Aggregate 定义不同 ConflictPolicy。

### 6. 队列治理

同步器按实体或 Aggregate 保证必要的因果顺序，同时允许无依赖实体并发上传。瞬时错误使用带 jitter 的指数退避；永久业务错误进入可诊断状态或 Dead Letter。大量连续可覆盖操作可以压缩，但具有副作用、审计意义或非交换语义的操作不能随意 compaction。

### 7. 多标签页同步

通过 BroadcastChannel 传播状态变化，由一个标签页持有同步 Leader Lease。Lease 必须有期限，并配合递增 fencing token；服务端或共享存储拒绝旧 token 的写入，解决被冻结 Leader 恢复后的脑裂问题。仅使用 `localStorage` 锁或心跳不足以提供可靠互斥。

### 8. Vue 3 响应式边界

Repository 返回领域实体，Pinia 保存当前页面真正需要的响应式投影。大型离线数据集不应全部转成深层 reactive 对象，可使用 `shallowRef`、规范化实体索引、分页工作集等方式控制 proxy 数量和依赖追踪成本。

### 9. Schema 与版本演进

IndexedDB schema、领域 payload schema 和同步协议分别版本化。迁移应可重入，并在修改持久数据前建立兼容策略。服务端在灰度期间至少支持一个明确的客户端兼容窗口；旧 mutation 可通过 migration adapter 转换，无法安全转换时不得静默丢弃。

### 10. 可观测性与数据完整性

除接口错误率外，应监控：Outbox backlog、最老 pending mutation age、冲突率、自动 merge 率、DLQ 数量、平均同步恢复时间、重复 operation 命中率和 Schema migration failure。关键数据可周期性执行客户端/服务端摘要或版本校验，以发现“请求成功但本地视图与权威状态已经分叉”的 silent divergence。

## 面试官判断标准

优秀候选人应把问题看作一个运行在浏览器中的**弱一致分布式系统**，能够讨论幂等、因果关系、版本、冲突语义、故障恢复和可观测性，并清楚指出哪些一致性问题必须交给服务端领域模型解决。

如果答案只是“Pinia 持久化 + IndexedDB + 网络恢复后重新请求”，通常尚未达到架构师级别。
