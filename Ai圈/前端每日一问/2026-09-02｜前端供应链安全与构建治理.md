# 2026-09-02｜前端供应链安全与构建治理

## 题目

你负责一个大型 Vue 3 + TypeScript 前端平台，采用 Monorepo，包含 80+ 内部包、300+ npm 直接/间接依赖，并由多个团队通过 CI/CD 独立发布。近期发生一起供应链安全事件：某个间接依赖的新版本被恶意篡改，在 CI 构建阶段读取环境变量并尝试向外部地址发送数据。

请设计一套**前端软件供应链安全与构建治理体系**。要求既能降低恶意 npm 包、依赖劫持和构建环境泄密的风险，又不能让研发效率严重下降。重点说明依赖准入、版本锁定、安装脚本治理、CI 隔离、密钥管理、产物可信、SBOM、漏洞响应、灰度发布和可观测性之间如何形成完整闭环。

## 背景 / 场景

平台存在以下现实约束：

- 业务团队每天可能合并数百个 PR，无法人工审核所有第三方依赖源码。
- 部分 npm 包依赖 `postinstall` / 原生构建脚本，不能简单全局禁用 lifecycle scripts。
- CI 中存在 npm registry token、Source Map 上传凭证、CDN 发布凭证等敏感信息。
- 多个业务应用共享内部组件库和构建插件，一个公共依赖事故可能产生较大的爆炸半径。
- 线上必须支持快速定位“某个页面最终包含了哪个第三方包版本”，并能够快速回滚。

## 核心考察点

- 是否理解 lockfile 只能解决版本确定性，不能证明依赖本身可信。
- npm 依赖准入、allowlist / denylist、依赖升级机器人与人工审批边界如何设计。
- 如何治理 `preinstall`、`install`、`postinstall` 等生命周期脚本，而不是简单执行 `npm install`。
- CI Runner 如何做到短生命周期、最小权限、网络隔离和 Secret 按阶段授权。
- 如何避免构建脚本直接接触生产发布密钥。
- 如何通过 immutable artifact、内容哈希、签名和 provenance 建立“源码 → 构建 → 产物 → 发布”的可信链路。
- SBOM 应如何关联应用版本、Git Commit、构建任务和线上 Release。
- Monorepo 下如何限制依赖污染的爆炸半径。
- 漏洞发现后如何判断实际影响，而不是看到 CVE 就全量紧急升级。
- 如何设计供应链事件的检测、阻断、回滚和审计能力。

## 追问方向

1. 已经有 `pnpm-lock.yaml` 并且 CI 使用 frozen lockfile，为什么仍然可能发生供应链攻击？
2. 如果全面使用 `--ignore-scripts`，哪些正常工程场景可能被破坏？你会如何设计例外机制？
3. 一个恶意 Vite 插件在构建阶段运行，它理论上能够读取哪些信息？如何缩小权限？
4. 为什么“不把 `.env.production` 提交到 Git”并不能解决 CI Secret 泄漏？
5. 如何证明 CDN 上运行的 `app.abc123.js` 确实来自某个 Git Commit，而不是 CI 被入侵后生成的恶意产物？
6. 如果安全扫描发现 lodash 某版本存在漏洞，但应用只使用不受影响的代码路径，你会立即阻断生产发布吗？为什么？
7. 一个内部公共构建插件被污染，如何快速确定哪些应用版本受到影响？
8. Monorepo 是否天然比 Polyrepo 更容易发生供应链事故？应该如何评价其真实风险？

## 参考答案要点

### 1. 先定义威胁模型，而不是堆安全工具

至少区分四类风险：**依赖本身恶意、合法包账号被接管、构建环境被入侵、发布链路被篡改**。不同威胁对应不同控制点。仅做 CVE 扫描只能覆盖其中很小一部分。

### 2. 依赖必须确定且经过准入

生产构建必须使用 lockfile + frozen install，禁止 CI 隐式更新依赖。新增直接依赖应经过自动策略检查，例如维护活跃度、发布时间异常、许可证、已知漏洞、安装脚本、包体积和依赖树变化。高风险变化进入人工审批，而普通 patch 升级可以自动化。

依赖升级 PR 应展示**依赖树 diff**，因为一次看似普通的直接依赖升级可能引入几十个新的 transitive dependencies。

### 3. Lifecycle Script 采用默认受限 + 显式授权

不应简单假设 npm 包安装脚本可信。可以默认禁止非批准包执行 lifecycle script，再维护经过审核的 allowlist。需要原生编译或代码生成的包应记录：包名、版本范围、为什么需要脚本以及负责人。

CI 还应限制安装阶段的网络访问，使依赖脚本不能任意向公网发送数据。理想情况下依赖获取通过内部 registry / proxy，并对外联目标执行 egress policy。

### 4. CI 按阶段隔离权限

将流水线拆为 install → test → build → sign → deploy，不让所有阶段共享同一组 Secret。

**构建阶段原则上不应该拥有生产 CDN 写权限。**构建只生成 immutable artifact；独立部署阶段在通过策略校验后获取短生命周期发布凭证。Runner 应尽量 ephemeral，任务结束即销毁，避免跨构建残留凭证和工作目录。

### 5. Secret 采用最小权限和短生命周期

优先使用基于工作负载身份的短期凭证，而不是长期 Token。Secret 应按 repository、environment、job 和权限范围切分，并防止 fork PR / 不可信代码路径获得生产 Secret。

需要特别注意：**任何能执行任意构建代码的依赖，本质上都处在 CI 的信任边界内。**因此 Secret 隔离比“扫描代码里有没有 `process.env`”更重要。

### 6. 构建一次，逐级晋升

生产环境不要重新执行一次 `npm install && build`。CI 应生成唯一 immutable artifact，并记录 Git Commit、lockfile hash、Node/pnpm 版本、构建镜像、构建任务 ID 和依赖清单。测试、灰度、生产使用同一份 artifact 逐级 promote，减少环境差异和二次污染机会。

### 7. 建立 Artifact Provenance

对产物生成内容哈希并进行签名；部署系统只接受来自可信构建身份、满足策略的已签名产物。这样安全边界从“相信某台 CI 机器”提升为“验证这个产物是谁、基于什么源码和依赖构建出来的”。

### 8. SBOM 必须能映射到线上版本

每个 Release 生成机器可读 SBOM，至少包含 package name、version、dependency relationship，并与以下信息关联：

- application / micro-app name
- release version
- Git Commit
- artifact digest
- deployment environment

线上错误监控和 Release Manifest 同样携带 release ID。发现某个恶意包版本后，应能够反向查询：**哪些当前在线 Release 包含它，以及影响了多少流量。**

### 9. Monorepo 要控制爆炸半径

Monorepo 的问题不是目录在一起，而是权限和依赖边界失控。可以通过 workspace dependency policy、CODEOWNERS、构建图、包级权限、affected build 和发布隔离限制影响范围。公共 build plugin、CLI、Babel/Vite 插件属于高权限代码，应比普通 UI 组件采用更严格的审核策略。

### 10. CVE 不等于实际可利用风险

漏洞响应需要结合版本、运行环境、调用路径、是否进入浏览器 bundle、是否仅为 devDependency，以及漏洞的 exploitability。生产阻断策略应基于风险等级，而不是简单“扫描到 High 就禁止所有发布”。但对于恶意包、凭证窃取类供应链事件，应采用更激进的立即隔离策略。

### 11. 可观测性覆盖构建与运行时

传统前端监控只覆盖浏览器运行时还不够。供应链体系还需要记录 dependency change、安装脚本执行、网络外联、artifact digest、签名结果、SBOM、deploy identity 和 release mapping。

当出现事件时，目标不是人工搜索几十个仓库，而是能回答：**谁引入 → 哪次构建包含 → 哪些产物受影响 → 哪些环境正在运行 → 如何一键阻断和回滚。**

## 面试官判断标准

优秀候选人通常会把问题拆成 **Source → Dependency → Build → Artifact → Deploy → Runtime** 六个信任边界，并讨论每个边界的身份、权限、完整性和审计机制。

如果答案只停留在 `npm audit`、Dependabot、锁版本和代码 Review，通常还没有达到架构师级供应链治理深度。
