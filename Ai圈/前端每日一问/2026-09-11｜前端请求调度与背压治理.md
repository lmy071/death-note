# 2026-09-11｜前端请求调度与背压治理

## 题目

你负责一个大型企业级 Vue 3 工作台。单个页面由 20+ 个业务模块组成，首屏会同时触发大量 API 请求；用户快速切换路由、筛选条件和 Tab 时，还会产生新的请求。线上逐渐出现以下问题：

- 弱网下请求大量排队，关键接口反而迟迟得不到执行；
- 用户连续修改筛选条件后，旧请求晚于新请求返回，覆盖了最新状态；
- 多个组件请求相同资源，产生重复流量；
- 路由离开后部分请求仍在运行，并继续修改已经失效的 Store；
- 服务端发生抖动时，前端 Retry 同时触发，进一步放大服务端压力；
- 浏览器 HTTP 连接、主线程解析 JSON、Vue 响应式更新同时出现资源竞争；
- 团队各自在组件中封装 axios/fetch，缺乏统一治理。

请你以**前端架构师**身份设计一套 Vue 3 企业应用的请求调度与背压架构。要求说明请求生命周期、优先级、并发控制、取消、去重、缓存、重试、状态一致性和可观测性，并解释为什么不能只依赖 `Promise.all`、axios interceptor 或组件级 `AbortController` 解决这些问题。

## 背景 / 场景

系统包含 Dashboard、搜索、报表、实时通知和复杂表格等模块。一次路由进入可能产生 30–80 个 HTTP 请求，其中既有影响首屏渲染的关键请求，也有预取、统计、低优先级推荐等非关键请求。

应用采用 Vue 3 Composition API + Pinia。多个团队独立开发业务模块，但共享统一 BFF。要求在网络波动、接口限流、用户高速交互以及局部后端故障时，仍能保证关键交互可用，并避免客户端形成请求风暴。

## 核心考察点

1. **请求调度层的架构位置**：是否能把 Transport、Scheduler、Cache、Domain State 与 Vue Component 解耦，而不是把网络生命周期散落在组件中。
2. **Priority + Concurrency Budget**：是否能区分 critical / interactive / background / prefetch，并建立全局与 endpoint/service 级并发预算。
3. **Backpressure**：请求生产速度超过网络、服务端或浏览器消费能力时，如何排队、合并、丢弃或降级，而不是无限创建 Promise。
4. **Cancellation 语义**：区分 UI 不再关心结果、客户端中止传输、服务端真正取消任务三个层次。
5. **Latest-wins 与状态一致性**：如何利用 request generation、sequence/version、query key 等机制防止旧响应覆盖新状态。
6. **Request Coalescing**：相同资源并发读取如何共享 in-flight Promise，同时处理不同订阅者的取消。
7. **Retry 治理**：Exponential Backoff、Jitter、Retry Budget、Retry-After、Circuit Breaker，以及为什么不能无条件自动重试写操作。
8. **缓存与失效**：Cache Key、TTL、SWR、ETag/If-None-Match 与 Domain Mutation 后的失效策略。
9. **Vue 3 响应式成本**：大量请求完成后 JSON parse、Store commit、computed/watch 更新可能形成第二阶段拥塞，如何批处理和隔离高频状态。
10. **可观测性**：如何测量 queue time、network time、parse time、commit time、cancel ratio、dedupe ratio、retry amplification、endpoint saturation。

## 追问方向

1. 浏览器已经支持 HTTP/2/HTTP/3 多路复用，为什么前端仍然需要并发限制？
2. 搜索框每次输入都会发请求。除了 debounce，还需要哪些机制保证最终一致性？
3. A、B 两个组件同时读取 `/user/123`，A 先卸载。若 A 调用 AbortController，是否应该终止底层 HTTP 请求？为什么？
4. 一个接口返回 429，并携带 `Retry-After`，Scheduler 应如何影响后续同服务请求？
5. GET 可以自动 Retry，那么 POST 是否一定不能 Retry？如何结合 Idempotency Key 设计？
6. 如果请求已经取消，但服务端仍然完成了扣款操作，前端应该如何恢复事实状态？
7. 如何避免 `Promise.all(100 requests)` 在弱网环境下制造客户端请求洪峰？
8. 请求调度器是否应该直接操作 Pinia Store？如果不应该，状态写入边界如何设计？
9. SSR 与 CSR 共用请求层时，哪些缓存、身份和请求上下文绝不能跨用户共享？
10. 如果后端整体延迟从 200ms 升高到 3s，前端如何通过 Adaptive Concurrency 或降级策略避免雪崩？

## 参考答案要点

### 1. 建立统一 Request Runtime，而不是组件直接控制网络

建议将链路拆为：

`Vue Component / Composable → Domain Query → Request Runtime → Scheduler → Transport → BFF`

Request Runtime 管理 Query Key、优先级、Deadline、Cancellation、Cache Policy、Retry Policy 和 Trace Context。组件表达“需要什么数据”，而不是决定底层 HTTP 应该何时以及如何执行。

Pinia 保存领域状态或 UI 状态，但不应承担通用网络调度器职责，否则网络策略会与业务状态强耦合。

### 2. Priority Queue + 分层并发预算

请求至少可分为：

- Critical：首屏、权限、核心业务状态；
- Interactive：用户当前点击、搜索、翻页；
- Background：统计、非关键刷新；
- Prefetch：预测性加载，可随时取消。

Scheduler 不仅设置一个全局 `maxConcurrency`，还应有 service/endpoint/resource class 级 Budget，防止某个慢服务占满全部执行槽位。

HTTP/2/3 的多路复用解决的是传输层连接利用率，并不意味着服务端 CPU、数据库连接池、浏览器 JSON 解析、内存和 Vue 更新能力无限，因此应用层仍需要 Admission Control。

### 3. 背压必须发生在创建无限工作之前

当队列持续增长，应根据请求语义执行：

- supersede：新搜索请求替代旧搜索请求；
- coalesce：相同 Query Key 合并；
- drop：丢弃已经没有价值的 prefetch；
- defer：后台请求延迟执行；
- degrade：切换到缓存或低成本接口；
- reject：超过 Deadline 的请求直接失败，而不是进入无意义队列。

关键指标应包含 queue duration，而不仅是传统 HTTP duration。

### 4. Cancellation 是传播协议，不只是 AbortController

每个逻辑请求应拥有生命周期 Scope，例如 route、component、interaction 或 task。Scope 销毁时通知 Runtime 取消订阅。

如果多个消费者共享一个 in-flight 请求，单个消费者离开通常只减少 subscriber；只有最后一个消费者取消，或请求整体已经失去价值时，才中止底层 fetch。

此外，Abort HTTP 并不能保证服务端业务事务停止。对于支付、任务创建等操作，客户端取消后仍需通过 operationId/idempotencyKey 查询最终事实状态。

### 5. 防止 stale response 覆盖最新状态

AbortController 不能作为唯一正确性机制，因为响应可能已经完成或取消无法传递到业务执行。

对高频查询应维护 query generation / sequence：

`queryKey + generation → result`

只有当前 generation 的响应才能提交到 View State。更复杂场景可以使用服务端 version、ETag 或 revision 做乐观并发控制。

### 6. Retry 必须有预算

正确策略不是“失败就重试 3 次”。应考虑：

- 是否属于 transient failure；
- HTTP method 是否幂等；
- 是否提供 Idempotency Key；
- Retry-After；
- exponential backoff + full jitter；
- endpoint Retry Budget；
- Circuit Breaker 状态。

如果 1 万客户端同时对故障接口执行固定间隔重试，会形成 Retry Storm，因此 Retry 本身也必须进入 Scheduler。

### 7. 缓存解决的不只是性能问题

读取请求可以使用 Query Key 建立 memory cache，并根据业务需求组合 TTL、SWR、ETag 和持久缓存。

Mutation 成功后不要简单 `clearAllCache()`，而应建立 entity/query dependency，例如修改 `user:123` 后只 invalidate 与该实体相关的查询。

### 8. 控制网络后的第二阶段背压

请求完成并不意味着性能问题结束。大量响应同时完成会触发 JSON parse、数据 normalize、Pinia 写入以及 Vue effect 执行。

可以通过 Worker 处理大型数据转换、批量 commit、`shallowRef`/`markRaw` 控制深层响应式成本，并将高频 transport progress 与稳定 domain state 分离，避免每个网络事件都触发组件树更新。

### 9. 可观测性需要覆盖 Scheduler

一次请求 Trace 可以拆分为：

`enqueue → admitted → requestStart → firstByte → bodyEnd → parseEnd → domainCommit → rendered`

除成功率和 P95 latency 外，还应观察 queue P95、active concurrency、cancel ratio、stale response ratio、dedupe hit rate、cache hit rate、retry amplification factor、429 rate 和 circuit-open duration。

这样才能区分“后端慢”“请求在客户端排队”“JSON 解析慢”还是“Vue commit 后渲染慢”。

### 10. 架构核心原则

成熟方案的重点不是封装一个更复杂的 `request()` 函数，而是建立统一的**请求资源治理层**：

> 网络请求是一种需要调度的有限资源。组件产生的是数据需求，Scheduler 决定何时执行；Domain 层决定结果是否仍然有效；Transport 只负责可靠传输。
> 

优秀候选人还应主动讨论 Deadline Propagation、Adaptive Concurrency、Load Shedding、Bulkhead、Idempotency、SWR、Trace Context，以及 SSR 中 request-scoped runtime 与用户数据隔离。
