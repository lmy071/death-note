# 2026-09-14｜AI Agent长任务状态恢复

## 题目

你负责一个基于 **Vue 3** 的企业级 AI Agent 工作台。Agent 可以执行持续 30 秒到 20 分钟的复杂任务，例如：检索企业知识库、调用多个 MCP/业务工具、生成代码、等待人工审批，再继续执行后续步骤。

当前实现由页面组件直接维护 `messages`、`toolCalls`、`loading` 等响应式状态，并通过一条 SSE 连接接收服务端事件。随着能力扩展，线上出现以下问题：用户刷新页面后任务状态丢失；网络重连后部分 Tool Call 重复显示甚至重复执行；同一会话在多个 Tab 打开时状态互相覆盖；用户点击“取消”后，后端某些工具仍继续执行；Agent 等待人工审批期间 SSE 长连接大量占用资源；模型或工具执行失败后无法判断应该 Retry、Resume 还是重新开始整个任务。

请你以**前端架构师**身份设计一套支持长任务、断线恢复、多端一致性、人工审批和可靠取消的 AI Agent 前端架构。要求说明 Vue 3 客户端状态模型、Agent Runtime 与 UI 的职责边界、事件协议、恢复机制、并发控制、故障处理以及可观测性方案，并说明关键技术权衡。

## 背景 / 场景

系统需要同时支持数万在线用户，一个 Agent Run 内可能产生数百个事件，并包含 LLM 推理、RAG、Tool Calling、MCP 工具以及 Human-in-the-loop 节点。

核心约束：

- Run 生命周期明显长于浏览器页面生命周期。
- SSE/WebSocket 只能作为实时事件传输通道，不能假设连接永久可靠。
- Tool Call 可能具有真实业务副作用，例如发送邮件、创建工单或修改数据。
- 用户可能刷新、关闭页面、切换设备或同时打开多个 Tab。
- Vue 组件需要实时展示 Token 流，但不能因为数千个 chunk 导致整个消息树频繁响应式更新。
- 用户取消操作需要尽可能向 LLM、RAG 和 Tool Execution 全链路传播，但已经发生的业务副作用不能假装被“撤销”。

## 核心考察点

- **Run 与 Connection 生命周期解耦**：是否意识到 Agent Run 是服务端持久化实体，而 SSE/WebSocket 只是该 Run 的一个实时观察通道。
- **事件驱动状态模型**：是否能设计带 `runId`、`eventId/sequence`、`stepId`、`attempt`、`timestamp` 的语义事件，而不是把 Token 字符串作为唯一协议。
- **状态机建模**：Run / Step / Tool Call 应具有明确状态及合法迁移，例如 `queued → running → waiting_approval → completed/failed/cancelled`。
- **断线恢复**：Snapshot + Event Replay、Last Event ID、序列号去重、Gap Detection、重放窗口和全量同步之间如何组合。
- **幂等与副作用边界**：前端去重只能解决 UI 重复；Tool Execution 必须由服务端通过 idempotency key / execution ID 保证业务幂等。
- **Vue 3 状态架构**：Server State、Ephemeral UI State、Streaming Buffer 分层，以及 Pinia/Composition API 与非深响应式数据结构的使用边界。
- **多 Tab / 多设备一致性**：BroadcastChannel 可以优化同浏览器协作，但服务端仍必须作为 authoritative state。
- **Cancellation 语义**：区分“停止继续调度”“中断可中断操作”和“补偿已产生副作用”，避免把 AbortController 等价为分布式事务回滚。
- **Human-in-the-loop**：审批是持久化 Workflow State，而不是依赖一条一直存活的 SSE 连接。
- **可观测性**：Run → Step → Model Call / Retrieval / Tool Call 的 Trace 关联，以及 TTFT、step latency、reconnect、replay、duplicate、cancel propagation 等指标。

## 追问方向

1. SSE 在 Token Streaming 场景足够简单，为什么还可能选择 WebSocket？什么情况下应该坚持 SSE + 普通 HTTP Command，而不是为了“双向通信”统一换成 WebSocket？
2. 客户端收到 `sequence=105` 后直接收到 `107`，你会如何处理？如果 106 永远无法从 replay log 中恢复呢？
3. 用户连续刷新 5 次导致建立 5 条连接，怎样避免 Run 被执行 5 次？“连接 Agent”和“创建 Agent Run”的 API 应如何分离？
4. Tool Call 已经成功创建工单，但浏览器在成功事件到达前断网；重连后用户再次点击执行，如何防止创建第二张工单？
5. 用户点击 Cancel 后模型停止生成，但某个第三方 API 不支持取消，此时 UI 应显示 `cancelled`、`cancelling` 还是其他状态？为什么？
6. 一个回答每秒产生几十个 Token chunk，直接每个 chunk 更新 Pinia 会出现什么问题？如何通过 buffer、批处理、`requestAnimationFrame` 或非响应式容器控制 Vue 更新频率？
7. 如果服务端 Event Log 只保存 10 分钟，而一个任务可能执行 20 分钟，Snapshot、Checkpoint 和 Replay 的边界应该如何设计？
8. 多 Tab 同时对一个 `waiting_approval` Step 点击 Approve / Reject，如何保证最终只有一个决策生效？
9. 如何设计 Retry？是重试整个 Run、失败 Step，还是单个 Tool Attempt？哪些 Tool 根本不能自动重试？
10. 如果 Agent 支持模型切换，Run 中途从模型 A 降级到模型 B，如何保证 Trace、Token Cost、上下文版本和用户界面仍可解释？

## 参考答案要点

### 1. 首先建立正确的生命周期模型

最重要的架构决策是：**Run 不属于 Vue 页面，也不属于 SSE Connection。**

建议至少形成以下层级：

```
Conversation
  └─ Run
      ├─ Step: LLM
      ├─ Step: Retrieval
      ├─ Step: Tool Call
      ├─ Step: Approval
      └─ Step: LLM
```

Run 创建后由 Agent Runtime 持久化和调度。浏览器只是通过 `GET /runs/:id` 获取 Snapshot，并通过事件流订阅增量变化。刷新页面相当于换了一个 Observer，而不是创建一个新 Run。

### 2. Command 与 Event 分离

建议将客户端协议拆成两类。

**Command：**

```
POST /runs
POST /runs/:id/cancel
POST /steps/:id/approve
POST /steps/:id/reject
POST /steps/:id/retry
```

**Event：**

```
run.started
step.started
llm.delta
llm.completed
tool.requested
tool.started
tool.completed
approval.required
step.failed
run.completed
run.cancel_requested
run.cancelled
```

这样可以避免把 WebSocket Connection 本身变成业务 API。即使实时连接断开，Command 仍可通过普通 HTTP 保持清晰的认证、幂等、Retry 和审计语义。

### 3. Event Envelope 必须支持恢复

事件不能只有 `{ type, data }`，至少需要稳定的身份和顺序信息，例如：

```tsx
interface AgentEvent<T = unknown> {
  runId: string
  eventId: string
  sequence: number
  stepId?: string
  attempt?: number
  type: AgentEventType
  timestamp: string
  payload: T
}
```

客户端记录最后确认的连续 `sequence`。重连时携带 cursor / Last-Event-ID，服务端从 Event Log 重放缺失事件。客户端必须按照 eventId/sequence 做幂等 Reduce，并在检测到 sequence gap 时停止盲目应用后续事件，进入 recovering 状态。

如果 Replay Window 已失效，则重新请求最新 Snapshot，并从 Snapshot 的 `version/lastSequence` 继续订阅。

### 4. Snapshot + Event Log，而不是无限 Event Sourcing

不必为了恢复能力把系统强制设计成永久 Event Sourcing。工程上可以使用：

```
Durable Snapshot + Bounded Event Log + Checkpoint
```

Snapshot 表示当前 authoritative state；短期 Event Log 服务于实时重连和诊断；Checkpoint 控制长 Run 的恢复成本。Event Log 过期时重新获取 Snapshot 即可。

### 5. Vue 3 客户端状态必须分层

不建议把所有 Token chunk 和网络对象全部塞进一个大型 Pinia Store。

可以拆为：

```
Server State
  Run / Step / Tool / Approval / Snapshot Version

Streaming State
  token buffers / partial tool arguments / transient deltas

UI State
  selected step / expanded panel / scroll / draft
```

Server State 可以进入 Pinia；高频 Token Streaming 可放在局部 buffer、`shallowRef`、普通 Map 或独立 streaming runtime 中，再按 animation frame 或固定时间窗口批量提交可见文本，避免每个 token 都触发大范围依赖追踪和组件更新。

组件通过 Composition API 的 selector/composable 订阅最小状态切片，而不是让整个 Chat Tree 依赖一个巨大 reactive object。

### 6. Tool Execution 的幂等不能依赖前端

每次有副作用的 Tool Execution 都应具有稳定 `executionId/idempotencyKey`。

例如：

```
runId + stepId + logicalAttempt
```

服务端 Tool Runtime 保存 execution record。即使浏览器断线、重试 HTTP 请求或事件重复投递，同一个 logical execution 都不能重复产生副作用。

前端 eventId 去重解决的是“不要显示两次”，并不能解决“不要发两封邮件”。

### 7. Cancellation 是协议，而不是 AbortController

取消应沿调用链传播：

```
UI
 ↓
Agent Runtime
 ↓
Scheduler
 ↓
LLM / Retrieval / Tool Runtime
 ↓
External Provider
```

Run 可以先进入 `cancel_requested/cancelling`。Runtime 停止调度新的 Step，并尝试中断支持取消的任务。对于无法取消且已经开始的外部 Tool，需要等待其确定结果，然后决定是否执行 Compensation。

因此 Cancellation 应定义为“停止系统继续推进，并尽力终止可终止工作”，而不是保证所有已经发生的副作用回滚。

### 8. Human-in-the-loop 是持久状态

`waiting_approval` 必须存储在服务端 Workflow State。此时完全可以关闭实时连接，用户数小时后重新打开页面仍然看到待审批状态。

Approve / Reject Command 应携带 expected version 或 decision token，通过 CAS / optimistic concurrency 保证只有第一个合法决策成功，其他 Tab 得到 conflict 并同步最新状态。

### 9. 多 Tab 优化不能改变权威来源

同浏览器可以使用 BroadcastChannel 共享 Run 更新、减少重复连接或通知其他 Tab 刷新状态，但不能把某个 Tab 选为业务事实的永久 Leader。

浏览器崩溃、设备切换和后台冻结都会破坏这种假设。最终一致性必须通过服务端 Snapshot/version 保证。

### 10. Retry 必须按照失败边界设计

Retry 不应只有一个通用按钮。

可以区分：

- LLM transient failure：通常允许自动 retry，并记录新的 attempt。
- Retrieval timeout：可按 Retry Budget 自动重试。
- 纯查询 Tool：通常可以安全 retry。
- 支付、发邮件、创建资源等副作用 Tool：必须依赖幂等能力，否则禁止自动 retry。
- Workflow invariant 被破坏：可能需要从 Checkpoint 恢复，而不是局部 retry。

Retry Policy 应属于 Runtime/Tool Policy，而不是散落在 Vue 组件里的 `catch(() => retry())`。

### 11. 可观测性围绕 Run 建立因果链

建议所有链路共享 `traceId/runId`，形成：

```
User Interaction
 → Run
   → Step
     → Model Call
     → Retrieval
     → Tool Execution
```

除普通错误率外，应关注 AI Agent 特有指标：TTFT、Token throughput、Run completion rate、Step latency、tool success rate、approval waiting time、reconnect count、replayed events、sequence gap、duplicate event、cancel propagation latency、retry count、model/token cost。

前端还应记录从事件到达至 UI 可见的 render latency，从而区分“Agent 慢”和“浏览器渲染慢”。

## 架构判断

优秀答案不应停留在“Pinia + SSE + AbortController”。真正需要识别的是：**长生命周期 AI Agent 本质上是一个可恢复的分布式 Workflow，而 Vue 3 前端只是这个 Workflow 的交互入口和状态投影。**

连接可以断，页面可以刷新，设备可以切换；只要 Run Identity、Durable State、Event Ordering、Idempotency 和 Command Concurrency 的边界设计正确，任务本身就不应该因此失去一致性。
