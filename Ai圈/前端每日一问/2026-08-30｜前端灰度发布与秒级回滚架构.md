# 2026-08-30｜前端灰度发布与秒级回滚架构

## 题目

你负责一个大型 Vue 3 + TypeScript B 端平台，采用 Monorepo，并由 10+ 个业务团队共同开发。平台每天可能发布数十次，部分模块通过微前端独立交付。近期发生过一次事故：公共权限 SDK 升级后只在特定租户 + 特定浏览器版本下触发异常，传统全量监控直到发布 20 分钟后才发现，回滚又因 HTML、CDN 资源与远程模块版本不一致导致部分用户持续白屏。

请设计一套支持 **渐进式灰度、自动异常检测、秒级止损、确定性回滚和完整版本追踪** 的前端发布架构。要求说明从 CI/CD、构建产物、版本寻址、灰度分流、运行时加载、Vue 3 应用启动、监控指标到回滚的完整链路，并解释如何避免“代码已经回滚，但用户仍加载到错误资源”的情况。

## 背景 / 场景

系统具有以下约束：

- 主应用与多个业务模块可以独立发布。
- 静态资源通过多层 CDN 分发，用户可能长期保持页面不刷新。
- Vue 3、Vue Router、Pinia、权限 SDK、埋点 SDK 等存在共享依赖。
- 平台存在不同租户、地区、浏览器、网络质量与账号权限组合。
- 发布必须支持 1% → 5% → 20% → 50% → 100% 的渐进式灰度。
- P0 故障目标是在发现异常后几十秒内停止继续扩大影响范围。

## 核心考察点

- 是否把发布系统视为一个**控制面 + 数据面**问题，而不是简单的 CDN 文件覆盖。
- 构建产物是否 immutable，是否通过 content hash / release ID 实现确定性版本寻址。
- HTML、manifest、JS/CSS、微前端 remote entry 之间如何建立原子版本关系。
- 灰度分流是在 CDN、Edge、BFF、配置中心还是客户端完成，各自有什么一致性和安全问题。
- 如何设计 Release Manifest，使一次发布可以精确描述主应用、子应用、共享依赖和配置版本。
- 如何把 Vue `app.config.errorHandler`、Promise Rejection、资源加载失败、接口错误、Web Vitals、Long Task 等信号关联到具体 Release。
- 自动回滚如何避免因瞬时流量、机器人、单一租户异常产生误判。
- Service Worker、HTTP Cache、CDN Cache 和浏览器内存中的旧 chunk 如何影响回滚。
- 微前端独立发布时如何限制故障爆炸半径。
- 如何设计兼容窗口，避免新旧前端版本与后端 API / Schema 不兼容。

## 追问方向

1. 为什么直接覆盖 `app.js` 或 `remoteEntry.js` 是危险的？content hash 能解决哪些问题，又不能解决哪些问题？
2. 如果 HTML 已经更新，但某个 CDN POP 仍缓存旧 manifest，会发生什么？如何保证发布指针与产物之间的一致性？
3. 灰度用户应该随机抽样，还是使用 `userId / tenantId` 做稳定哈希？为什么？
4. 一个租户错误率突然达到 80%，但全局错误率只有 0.05%，自动发布系统应该如何判断？
5. Vue 3 应用启动阶段发生异常，监控 SDK 自己尚未初始化，如何捕获？
6. 用户打开页面 8 小时没有刷新，此时系统已经发布 6 个版本。动态 import 一个新模块时如何避免 chunk 版本漂移？
7. 微前端子应用需要紧急回滚时，是否必须回滚主应用？怎样设计才能做到独立止损？
8. Service Worker 缓存了错误版本时，服务器端回滚为什么可能无效？你会如何设计缓存版本与激活策略？
9. 后端已经执行不可逆 Schema 变更，前端还能否直接回滚到两个版本之前？如何通过 API 兼容窗口解决？
10. 如何证明“自动回滚”真的有效，而不是事故发生时才第一次验证？

## 参考答案要点

### 1. 发布产物必须不可变

每次构建生成唯一 `releaseId`，JS/CSS/图片使用 content hash，已经发布的资源禁止覆盖。CDN 上的 `/assets/a.abc123.js` 应永远代表同一份字节内容。真正发生变化的是一个体积极小的**版本指针 / Release Manifest**，而不是覆盖历史产物。

这样回滚的本质不是重新构建旧代码，而是把流量重新指向已经验证过的旧 Release，因此可以把恢复时间从分钟级压缩到秒级或十秒级。

### 2. Release Manifest 作为版本真相源

一次 Release 应记录：主应用版本、各微前端版本、共享 SDK 版本、构建时间、Git SHA、配置 Schema、兼容 API 版本、资产完整性信息等。

运行时只能加载 Manifest 中确定的版本，禁止使用 `latest`。主应用与子应用之间使用显式版本映射，从而能够回答“这个用户此刻实际运行的是哪组代码”。

### 3. 灰度需要稳定且可解释

使用用户、租户或设备维度的稳定哈希，而不是每个请求重新随机。否则同一用户可能在页面导航过程中不断进入不同 Release。

灰度规则应支持租户、地区、浏览器版本、账号、内部员工等维度，同时服务端签发最终 Release，客户端不能通过修改 LocalStorage 自行进入高权限或未公开版本。

### 4. 发布控制面与运行时数据面分离

CI/CD 负责构建、测试、签名、上传 immutable assets；Release Controller 管理版本状态和流量权重；Edge/BFF 根据灰度策略解析当前 Release；浏览器只消费已经解析好的 Release Manifest。

发布状态可以建模为 `Built → Verified → Canary → Progressive → Stable → RolledBack`，所有状态迁移必须可审计。

### 5. 自动异常检测不能只看全局错误率

需要按 `releaseId + appId + tenant + browser + route + region` 等维度切片，并比较 Candidate 与 Stable 的基线差异。

核心指标至少包括：启动失败率、JS Error、Unhandled Rejection、资源加载失败、关键 API 失败率、白屏率、核心业务成功率，以及 LCP / INP 等体验指标。自动回滚应综合最小样本量、绝对阈值、相对基线恶化程度和持续窗口，避免单个瞬时异常触发抖动。

### 6. 启动阶段需要 Early Error Capture

监控不能等 Vue 完成 mount 后才初始化。应在应用 bootstrap 最早阶段安装 `window.onerror`、`unhandledrejection`、资源加载错误监听，并暂存在内存队列；正式 Telemetry SDK 初始化后再补发。

Vue 创建后再接入 `app.config.errorHandler`，同时记录 `releaseId`、route、appId 和组件上下文，使运行时异常可以精确归因。

### 7. 回滚必须处理缓存一致性

HTML / Release Pointer 使用短缓存或可重新验证策略；hash assets 使用长期 immutable cache。回滚时只切换 Release Pointer，而历史 hash assets 无需 purge。

这比“覆盖 JS 后全网清 CDN”可靠得多，因为 CDN purge 本身具有传播延迟，也无法清除已经进入浏览器缓存或 Service Worker Cache Storage 的资源。

### 8. 长会话需要版本固定

一次页面会话应绑定一个 Release Snapshot。动态 import、远程模块和共享依赖都从同一 Snapshot 解析，避免用户打开旧 HTML 后动态加载到新版本 chunk。

如果新版本与旧版本无法长期共存，应检测 Release 过期并提示安全刷新，而不是让运行时静默混用两个版本。

### 9. 微前端必须具备独立故障域

每个子应用拥有独立 releaseId、健康指标和回滚指针。主应用通过 Manifest 决定具体加载哪个子应用版本；某个子应用异常时可以单独回退到上一个 Stable，而不必整体回滚平台。

共享 Vue 3、Router、Pinia 或公共 SDK 时需要兼容矩阵与平台基线，否则所谓“独立发布”仍可能因为共享运行时升级造成全局故障。

### 10. 前后端采用 Expand / Contract 兼容策略

前端回滚能力依赖后端保持一定版本兼容窗口。数据库和 API 演进应优先新增字段 / 新接口，等待旧前端自然退出后再删除旧能力。

如果后端已经执行破坏性且不可逆的 Schema 变更，那么“前端可以任意回滚”就是错误假设。Release 系统应记录兼容范围，并阻止回滚到不兼容版本。

### 11. 自动回滚本身也需要工程化验证

定期进行发布故障演练：注入 JS 启动异常、错误 remote URL、接口高失败率、错误 CDN 缓存策略等，验证监控是否发现、控制面是否停止扩量、Release Pointer 是否正确回退，以及真实浏览器是否恢复。

关键指标应包括 **MTTD（发现时间）** 与 **MTTR（恢复时间）**，而不只是发布成功率。

## 面试官判断标准

优秀候选人应把问题抽象成 **版本一致性、流量控制、故障检测和故障域隔离**，而不是只回答“蓝绿发布 + Sentry + CDN 回滚”。如果能够主动讨论 immutable artifacts、Release Manifest、稳定哈希、长会话版本固定、Service Worker 缓存、微前端独立回滚、前后端兼容窗口，以及自动回滚的误报控制，基本具备大型前端交付体系的架构设计能力。
