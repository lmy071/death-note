# 2026-09-03｜生成式 UI 安全渲染架构

## 题目

你正在设计一个基于 Vue 3 的企业级 AI Copilot。大模型不仅返回文本，还可以根据用户意图动态生成表单、数据表格、图表、审批卡片、导航入口等 UI，并通过 Tool Calling 获取业务数据或触发操作。

系统需要支持多个模型、多个业务域和第三方 MCP/Agent 工具，同时满足低延迟流式体验。请设计一套可长期演进的 **生成式 UI（Generative UI）前端架构**，重点说明：如何定义模型到 UI 的协议、如何安全地把模型输出映射成 Vue 组件、如何管理流式 UI 状态、如何隔离工具权限，以及如何避免模型输出直接获得任意前端执行能力。

## 背景 / 场景

业务平台已有 100+ 个 Vue 3 业务组件。产品希望 AI 可以按上下文动态组合这些能力，例如：

- 用户输入“帮我创建一个高优先级工单”，AI 动态展示工单表单并预填字段；
- 用户询问销售数据时，AI 返回查询结果并动态生成图表；
- AI Agent 调用多个工具后持续更新同一张任务卡片；
- 不同模型可能输出不同版本的 UI Schema；
- 第三方工具可能返回不可信数据；
- 某些 UI 操作具有写入、审批、删除等高风险副作用。

要求系统能够灰度升级协议和组件，同时保证旧会话仍然可恢复，并能够追踪“哪个模型输出 → 哪个 Schema → 哪个组件 → 哪次 Tool Call → 哪个用户操作”。

## 核心考察点

- **Schema-first 协议设计**：模型输出声明式 UI Schema，而不是 HTML、Vue SFC、JavaScript 或可执行代码；Schema 应包含组件类型、Props、数据绑定、Action、版本等稳定字段。
- **Component Registry / Capability Registry**：模型只能引用经过平台注册的组件和能力；Registry 负责 Schema → Vue Component 的可信映射、版本兼容和权限元数据。
- **信任边界**：区分 Model Output、Tool Result、Application State 与 User Input，所有跨边界数据都必须验证，不能因为来自模型或 MCP Server 就默认可信。
- **运行时校验**：使用 JSON Schema、Zod 等机制验证结构、字段范围和 Action 参数，并考虑未知字段、Schema 版本和向前/向后兼容。
- **禁止任意代码执行**：不能通过 `v-html`、`eval`、`new Function`、动态模板编译或模型生成事件处理器来实现 Generative UI。
- **Action 与 Tool Calling 分层**：UI Action 只表达意图，例如 `submitTicket`；实际工具调用由受控 Action Dispatcher / BFF / Agent Runtime 完成，并执行鉴权、参数校验和审计。
- **高风险操作确认**：删除、付款、审批、权限变更等操作需要 Human-in-the-loop，模型不能通过生成 UI 绕过确认流程。
- **流式 UI 状态模型**：需要处理 Schema Patch、Token Stream、Tool Event、取消、重试、乱序和重复事件，避免每个 Token 都触发 Vue 大范围响应式更新。
- **状态所有权**：区分 Conversation State、Agent Execution State、Generated UI State 与业务 Server State，避免把全部状态塞进一个 Pinia Store。
- **协议演进**：Schema 和组件能力都需要版本化；旧会话恢复时必须能够解释历史 Schema，不能让组件升级导致历史消息不可渲染。
- **可观测性**：建立 traceId / conversationId / runId / schemaVersion / componentVersion / toolCallId 等关联字段，能够重建一次生成式 UI 的完整执行链路。
- **故障降级**：未知组件、Schema 校验失败、工具超时、模型输出损坏时，应降级为安全文本、静态卡片或可重试状态，而不是让整个对话页面崩溃。

## 追问方向

1. 为什么不能让模型直接输出 Vue Template，然后使用运行时编译器渲染？即使部署了 CSP 是否足够安全？
2. Component Registry 中应该保存哪些元数据？如何让模型知道“哪些组件可以使用”，但又不把前端内部实现暴露给模型？
3. 如果模型在流式过程中先生成 `Chart`，随后又把它修改为 `Table`，前端应该采用完整 Schema 重放还是 Patch 协议？如何保证 Patch 顺序？
4. 一个生成式表单中的 `submit` 最终会删除生产数据。前端、Agent Runtime 和后端分别承担什么权限责任？
5. MCP Server 返回一段包含 HTML、Markdown 链接和工具指令的字符串，应该如何处理？为什么 Tool Result 仍属于不可信输入？
6. Vue 3 中如何设计 Generated UI Renderer，避免动态组件树导致响应式依赖失控和频繁重渲染？
7. Schema v3 已上线，但用户打开了三个月前由 Schema v1 创建的历史会话。如何保证它仍然可渲染？
8. 如果某个组件版本上线后错误率突然增加，如何快速确定是模型行为变化、Schema 变化、组件 Bug 还是 Tool Result 异常？

## 参考答案要点

### 1. 模型输出应该是声明，而不是实现

推荐把模型约束为输出有限 DSL / JSON Schema，例如 `type: "ticket-form"`、`props`、`bindings`、`actions`。前端 Renderer 只解释平台定义的语义。

模型不应该输出任意 HTML、Vue Template 或 JavaScript。否则模型实际上获得了部分代码生成与执行权限，Prompt Injection、第三方 Tool Result 或模型幻觉都可能转化成 XSS、越权调用或任意逻辑执行问题。

### 2. 建立 Component / Capability Registry

Registry 是 Generative UI 的核心安全边界之一。每个能力至少描述：

- 稳定的 capability/component ID；
- Props Schema；
- 支持的 Action；
- 风险等级；
- 所需权限；
- Schema / Component 版本；
- 可使用的业务域；
- fallback renderer。

模型看到的是能力描述和稳定协议，而不是 Vue 组件源码。前端通过 Registry 将合法 ID 映射到本地受信任组件。

### 3. Action 不能等价于函数调用

Schema 中可以声明 `action: "ticket.create"`，但不能携带函数代码或任意 URL。点击后进入统一 Action Dispatcher，由它负责参数校验、权限检查、幂等、确认流程、审计和调用 Agent/BFF。

尤其不能把模型返回的函数名直接用于类似 `component[actionName](args)` 的动态调用，而应通过显式 allowlist 做 capability dispatch。

### 4. 权限必须以后端为最终边界

前端隐藏按钮只能改善 UX，不能构成安全机制。高风险 Tool Call 应由后端根据当前用户身份、租户、资源权限和操作风险重新授权。

对于 destructive action，可采用 `propose → preview → user approve → execute` 的两阶段协议，并让 approval 与具体参数、资源版本和短期 token 绑定，避免用户确认后参数被模型偷偷替换。

### 5. 流式协议应采用事件模型

不要把整个 AI 响应看成一个不断变化的大字符串。可以设计：

`run.started → ui.created → ui.patch → tool.started → tool.completed → ui.patch → run.completed`

每个事件包含 `runId`、`eventId`、`sequence` 和版本。客户端通过 reducer/projector 构建 Generated UI State，从而实现去重、顺序校验、恢复和 replay。

高频 Token 可以在非响应式 buffer 中累积，并按照 animation frame 或固定时间窗口批量提交到 Vue 状态，减少响应式触发。

### 6. Vue 3 Renderer 需要明确响应式边界

Schema 原始对象不一定需要深度 reactive。大型 Schema 可以使用 `shallowRef`、不可变快照或规范化实体存储；Patch 只更新受影响节点。

动态组件通过受控 Registry 解析，不允许模型提供任意 import path。对于昂贵组件可使用异步组件、局部 Suspense、虚拟化和独立 Error Boundary，避免一个生成节点拖垮整棵会话树。

### 7. 协议和历史数据必须可演进

持久化的不应只是最终 DOM，而应保存稳定 Schema、Schema Version、必要的 Tool Result Snapshot 和执行元数据。

升级时可采用：

`v1 persisted schema → migration/adapter → canonical schema → current renderer`

对于无法迁移的历史能力，保留兼容 Renderer 或退化为静态表示。不要假设当前最新版组件永远能解释历史数据。

### 8. 可观测性必须贯穿 AI 与 UI

一次交互至少关联：模型与版本、Prompt/配置版本、conversationId、runId、Schema Version、组件 ID/版本、Tool Call、渲染耗时、校验失败、用户 Action 和后端 Trace。

这样当某个组件错误率升高时，才能按模型版本、Prompt、Schema、组件 Release 或 Tool Provider 切片定位问题，而不是只有一条笼统的“AI 页面报错”。

### 9. 必须设计安全降级

Renderer 对未知 capability、非法 Schema、超限 payload、工具失败等情况采用 fail-closed：拒绝执行副作用，并降级到受控文本/错误卡片。

生成式 UI 的核心原则可以概括为：**模型负责提出 UI 意图，可信应用负责解释和执行；模型永远不直接拥有任意 UI 代码执行权或业务权限。**

## 面试官判断标准

优秀候选人应该能够把 Generative UI 看成 **协议系统 + Capability Runtime + 安全边界 + 状态投影系统**，而不仅是“LLM 返回 JSON 后用 `<component :is>` 渲染”。

如果候选人能够进一步讨论 Schema 演进、Tool 权限、Human-in-the-loop、事件重放、旧会话兼容、灰度发布和跨 AI/UI/Tool 的可观测链路，基本达到架构师级别。
