# 2026-08-26｜大型 B 端 Vue 3 前端架构设计

## 题目

你正在设计一个大型 B 端平台，包含 20+ 个业务域、100+ 个页面、多个独立团队并行开发。技术栈统一为 Vue 3 + TypeScript，但不同业务域发布节奏不同，并且部分页面需要 SSR，部分页面需要纯 CSR。

请设计一套可长期演进的前端架构，重点说明：**应用拆分边界、运行时隔离、共享依赖策略、状态管理边界、路由与权限、构建与发布、可观测性、故障降级，以及如何避免微前端带来的复杂度失控。**

## 核心考察点

- 是否能从组织边界、业务边界和技术边界共同定义应用拆分，而不是机械按页面拆分
- Vue 3 场景下共享运行时依赖时，如何处理 Vue 单例、Pinia、Router、UI 库和公共 SDK 的版本治理
- SSR 与 CSR 混合架构下，服务端渲染边界、数据预取、Hydration 一致性和缓存策略
- 全局状态与领域状态如何隔离，如何避免跨应用隐式依赖
- 微前端通信机制如何设计成显式契约，而不是共享全局变量或 EventBus 泛滥
- 如何进行独立构建、灰度发布、回滚、资产版本管理与 CDN 缓存治理
- 如何构建统一的性能、错误、链路、发布版本和用户行为可观测体系
- 如何设计熔断、降级、超时、失败隔离和局部不可用时的用户体验

## 追问方向

1. 如果多个子应用必须共享同一个 Vue 3 运行时，如何保证不会因为版本不一致导致响应式系统或组件上下文异常？
2. Pinia 应该全局共享还是每个业务域独立？什么场景下允许跨域读状态？
3. 如果某个子应用发布后出现白屏，主应用应如何自动发现并降级？
4. SSR 页面中嵌入 CSR 子应用时，如何避免 Hydration mismatch？
5. 如果公共组件库升级导致 5 个业务域出现兼容性问题，如何从架构和发布体系上降低爆炸半径？
6. 你会在什么条件下明确反对使用微前端？

## 参考答案要点

### 1. 应用拆分

优先按照 **业务领域 + 团队所有权 + 独立发布需求** 划分，而不是按照页面数量划分。一个子应用应具备清晰的领域模型、相对完整的用户场景以及独立发布价值。若两个模块长期共享状态、组件和发布节奏，则通常不应该强行拆成两个微前端。

### 2. 运行时与依赖治理

Vue 3、Vue Router、Pinia 等核心运行时需要有明确的单例策略和兼容矩阵。共享依赖不能只依赖 semver 范围，应建立平台级版本基线、升级窗口和兼容性验证。公共 UI、埋点 SDK、权限 SDK 应采用稳定契约和版本化发布，避免子应用直接依赖主应用内部实现。

### 3. 状态边界

领域状态默认归属各自子应用。跨应用共享的数据应尽量提升为后端状态、URL 状态或显式平台服务；只有真正属于“平台级会话”的状态，例如用户身份、租户、语言、主题，才适合作为共享状态。跨域访问应通过只读接口或事件契约，而不是直接 import 对方 store。

### 4. 通信机制

通信应分层：URL/路由用于导航状态；后端或 BFF 用于业务数据；平台 SDK 用于稳定能力；事件机制只处理低耦合通知。所有跨应用事件应有事件名、Payload Schema、版本和所有者，禁止无治理的全局 EventBus。

### 5. SSR / CSR 混合

SSR 只覆盖真正需要首屏、SEO 或低端设备性能收益的页面。服务端数据预取结果需要序列化并与客户端初始化数据保持一致；客户端挂载前必须确保 DOM、权限判定、随机值、时间相关逻辑一致。CSR 子应用可在 SSR 外壳完成 Hydration 后再延迟挂载，避免服务端与客户端渲染树不一致。

### 6. 构建与发布

每个业务域独立构建和发布，但必须经过统一平台治理，包括版本清单、资产完整性校验、灰度、回滚、依赖兼容检测和缓存策略。生产环境不应通过“永远指向 latest”的方式加载子应用，而应通过可追踪的 manifest 或版本映射加载确定性资产。

### 7. 可观测性

至少统一采集：应用名、子应用版本、主应用版本、路由、用户会话、接口链路、JS Error、Promise Rejection、资源加载失败、Vue errorHandler、性能指标和发布批次。这样才能把一次线上故障快速定位到具体业务域和版本。

### 8. 故障隔离与降级

主应用应对每个远程模块设置超时、加载失败兜底和 Error Boundary；关键页面要具备静态兜底或降级入口。子应用崩溃不应拖垮主框架，公共 SDK 失败也应避免阻塞业务主流程。

### 9. 什么时候不该用微前端

当团队规模较小、代码库可控、发布节奏一致、没有明显领域边界时，Monorepo + 模块化通常比微前端更简单。微前端的价值主要来自**组织解耦和独立交付**，而不是单纯的代码拆分。

## 面试官判断标准

优秀候选人不会只讨论 qiankun、Module Federation 等具体框架，而会先讨论边界、治理、组织结构、故障域和演进成本；同时能够明确指出微前端的收益、代价及适用条件。
