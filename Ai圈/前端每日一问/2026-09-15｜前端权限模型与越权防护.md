# 2026-09-15｜前端权限模型与越权防护

## 题目

你负责一个大型企业级 Vue 3 管理平台，包含主应用、多个独立部署的微前端，以及通过 BFF 聚合的数十个业务服务。系统支持动态菜单、页面级权限、按钮级权限、字段级权限和数据范围权限（如“本人 / 部门 / 全公司”）。

当前实现中，前端会在登录后获取一份权限列表，通过路由守卫、`v-if` 和 Pinia 判断用户是否能看到页面或操作按钮。随着业务增长，出现以下问题：

- 微前端之间权限模型不一致，同一个权限在不同应用中含义不同；
- 用户修改请求参数后可以调用 UI 中不可见的操作；
- 权限变更后，已打开页面仍可能保留旧权限并继续提交请求；
- 多租户场景偶发跨租户缓存污染；
- SSR/BFF 返回的数据有时包含当前用户本不应看到的字段；
- 为了“安全”，部分团队把大量业务授权规则复制到前端，导致前后端规则逐渐漂移。

请以**前端架构师**身份设计一套可长期演进的权限与授权架构。说明前端、BFF、后端服务各自应该承担什么职责，并重点回答：**前端权限控制究竟能提供什么安全保证，哪些事情绝不能依赖前端完成？**

## 背景 / 场景

平台采用 Vue 3 Composition API + Pinia + Vue Router，多个团队通过微前端独立交付业务模块。登录使用统一身份系统，后端存在 RBAC 与部分 ABAC 规则。平台需要同时满足用户体验、独立部署、权限实时变更、多租户隔离和审计要求。

目标不是设计一个 `hasPermission()` 工具函数，而是建立统一的 **Authentication → Authorization → Data Filtering → UI Capability Projection → Audit** 链路，并控制权限规则在不同层之间的所有权。

## 核心考察点

1. **Authentication 与 Authorization 边界**：Token 能证明身份，不等于证明当前操作被授权；前端持有 Token 也不能成为授权主体。
2. **Server-side Enforcement**：所有具有安全意义的资源访问、数据范围、字段读取和写操作必须由可信服务端重新授权，不能依赖路由守卫、按钮隐藏或前端传入的角色字段。
3. **Capability Projection**：前端应消费服务端计算后的 capability，例如 `order.read`、`order.refund`、`customer.phone.read`，主要用于 UI 投影和 UX，而不是复制完整授权决策引擎。
4. **RBAC / ABAC / ReBAC 权衡**：解释角色、属性和资源关系分别适合解决什么问题，以及为什么大型系统通常需要组合模型。
5. **微前端权限契约**：建立平台级 Permission/Capability Schema、版本策略和命名空间，避免各子应用自行解释 `admin`、`editor` 等模糊角色。
6. **权限生命周期**：登录后的权限不是永久 Snapshot；需要考虑权限撤销、租户切换、组织关系变化、长页面会话以及敏感操作执行前重新授权。
7. **多租户隔离**：Tenant Identity 必须进入服务端授权上下文和缓存键；不能相信前端传入的 `tenantId` 就代表用户有权访问该租户。
8. **字段级数据安全**：SSR、BFF 和 API 必须在数据离开可信边界前完成字段过滤；前端“拿到后不显示”不属于数据安全。
9. **缓存安全**：分析 CDN、BFF Cache、Service Worker、Pinia 持久化和 IndexedDB 中权限敏感数据的 Cache Key、失效与清理策略。
10. **可观测与审计**：授权拒绝需要关联 `user / tenant / resource / action / policyVersion / traceId`，同时避免日志泄露敏感数据。

## 追问方向

1. 如果前端刚渲染出“退款”按钮，管理员随后撤销了用户权限，而用户此时点击按钮，系统应该如何保证安全和 UX 一致性？
2. Capability API 应返回角色、权限字符串，还是针对当前资源计算后的操作能力？三种方案分别有什么扩展性和性能问题？
3. 一个订单是否允许编辑取决于“用户所属部门 + 订单所属区域 + 当前订单状态 + 金额阈值”，你会把这套 ABAC 判断放在哪里？前端需要知道多少规则？
4. 微前端 A 使用 `order.edit`，微前端 B 使用 `canModifyOrder`。如何通过契约、CI 和运行时治理避免语义漂移？
5. 用户从租户 A 切换到租户 B 时，Pinia、Query Cache、IndexedDB、Service Worker Cache 和正在执行的请求分别应该如何处理？
6. 如果 Capability API 本身出现 5 秒延迟或不可用，应该 Fail Open 还是 Fail Closed？普通 UI 与高风险操作是否应采用相同策略？
7. SSR 首屏已经把无权限字段写进 HTML，客户端 Hydration 后再删除，是否安全？为什么？
8. 如何防止攻击者直接调用 BFF API、修改 `tenantId`、`userId`、`role` 或重放旧请求实现越权？
9. 是否应该让前端拥有完整 Policy Engine，从而做到“前后端同构授权”？什么情况下这种方案可能有价值，什么情况下会制造新的安全风险？
10. 如何测试权限系统？除了单元测试，还应如何设计 Contract Test、Policy Test、越权测试和多租户隔离测试？

## 参考答案要点

### 1. 首先定义信任边界

浏览器属于**不可信执行环境**。用户可以修改 JavaScript、Pinia State、DOM、请求参数甚至完全绕过 UI 直接调用 API。因此：

> 前端权限控制的主要价值是 Capability Projection 与用户体验治理，而不是建立真正的安全边界。
> 

`router.beforeEach`、权限指令、组件条件渲染都只能减少误操作和隐藏无意义入口。真正的授权必须发生在 BFF / API / Domain Service 等可信执行环境。

### 2. 建立统一授权链路

推荐将一次操作抽象为：

```
Identity
  ↓
Authenticated Principal
  ↓
Authorization Context
(user, tenant, resource, action, environment)
  ↓
Policy Decision Point
  ↓
Permit / Deny + Constraints
  ↓
Domain Operation
  ↓
Audit Event
```

客户端只消费服务端授权结果的投影，不自行成为 Policy Decision Point 的权威实现。

### 3. Capability 优于直接暴露角色

不要让大量 Vue 组件出现：

```tsx
if (user.role === 'admin')
```

组件更适合依赖稳定的领域能力：

```tsx
capabilities.can('order.refund', order.id)
```

但 `can()` 的客户端结果仍只是 UI Hint。真正执行退款时，服务端必须针对当前 Principal、Tenant、Order 和 Policy Version 再做授权。

角色属于组织模型，Capability 属于应用契约，两者不应强耦合。

### 4. RBAC + ABAC 分层

RBAC 适合表达稳定、粗粒度职责，例如客服、财务管理员；ABAC 适合表达动态条件，例如订单金额、部门、区域、资源状态和时间窗口。

复杂系统通常由服务端 Policy Engine 将这些条件统一计算，再向前端输出必要的 capability 或约束，而不是把完整规则复制进 Vue 应用。

### 5. 权限撤销必须考虑 TOCTOU

前端获取 capability 到用户真正执行操作之间存在 Time-of-check / Time-of-use 窗口。

因此敏感操作应在执行时重新授权。若权限已经撤销，服务端返回明确的 `403 + authorization reason code`；前端收到后刷新 capability、撤销乐观状态并给出可理解的提示。

不能因为按钮在 30 秒前可见，就认为本次请求仍然合法。

### 6. 多租户必须从身份上下文绑定

Tenant 不能只是普通请求参数。服务端需要验证：

```
principal ∈ tenant
AND principal can action resource
AND resource.tenantId == authorizedTenant
```

缓存也必须至少绑定 Tenant / Principal / Policy-sensitive Dimension。租户切换时应 Abort 旧请求、清理用户态 Query Cache、Pinia 敏感状态以及持久化缓存，避免旧租户响应晚到后污染新租户状态。

### 7. 数据最小化发生在服务端

如果用户无权读取 `customer.phone`，BFF/API 就不应把电话号码发送到浏览器。

以下方案都不安全：

```
API 返回完整数据
        ↓
Vue 根据权限隐藏字段
```

因为数据已经进入浏览器，可通过 DevTools、网络记录、SSR HTML 或缓存读取。

正确原则是 **Filter Before Egress**。

### 8. 微前端使用统一 Capability Contract

平台层维护稳定的命名空间，例如：

```
order.read
order.edit
order.refund
order.export
customer.phone.read
```

并通过 Schema、TypeScript SDK、契约测试和废弃策略管理版本。微前端拥有 UI 实现自治权，但不能自行重新定义 capability 的安全语义。

### 9. Fail Closed 与 UX 降级分离

授权服务不可用时，高风险写操作应默认 Fail Closed。

对于普通页面展示，可以利用短生命周期、经过服务端签发或缓存的 capability snapshot 做有限降级，但必须明确 TTL、Scope 和失效策略。不能为了可用性无限复用旧权限。

安全决策与 UI 可用性降级应被当成两个不同问题处理。

### 10. 建立授权可观测性

建议为每次关键授权记录结构化 Decision：

```
authorization.decision
├─ principalId
├─ tenantId
├─ action
├─ resourceType
├─ resourceId
├─ decision: permit | deny
├─ reasonCode
├─ policyVersion
└─ traceId
```

这样可以回答“为什么这个用户昨天能操作、今天不能”“是否存在某个租户异常高的 Deny Rate”“某次 Policy 发布是否造成大面积误拒绝”等问题。

同时对 ID、属性、Policy Input 做数据最小化，避免可观测系统本身成为敏感信息泄露源。

### 11. 工程治理

权限架构最终应形成平台级约束，而不是依赖开发者记忆：统一 Capability Registry、TypeScript SDK、ESLint/静态检查禁止直接判断敏感 Role、契约测试、Policy CI、越权集成测试、多租户隔离测试，以及权限变更的审计与灰度发布机制。

**最终架构原则：** 前端负责“用户当前应该看到和能够尝试什么”，可信服务端负责“这个请求此刻是否真的允许执行”。任何只存在于浏览器中的权限判断，都不能被视为安全控制。
