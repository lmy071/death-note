# 2026-09-16｜生成式 UI 协议与安全治理

## 题目

你负责设计一个基于 **Vue 3** 的企业级 AI 工作台。LLM / Agent 不再只返回 Markdown 文本，而是可以根据用户意图动态生成表单、数据卡片、审批面板、图表和可执行操作，即 **Generative UI**。

请设计一套可生产落地的生成式 UI 架构，使模型能够动态决定“展示什么 UI”，但不能直接获得任意组件执行能力。重点说明：**模型输出协议、组件注册体系、运行时校验、状态管理、流式渲染、权限与安全边界、版本兼容、故障降级和可观测性**。

## 背景 / 场景

现有 AI Chat 仅支持 Markdown。业务希望 Agent 可以逐步生成复杂交互，例如：

1. 用户输入“分析本月异常订单并让我处理高风险订单”。
2. Agent 先流式输出分析过程，同时生成风险订单表格。
3. 用户点击某条订单后，Agent 动态生成订单详情卡和退款表单。
4. 用户填写金额并点击“提交退款”。
5. UI 需要调用受控 Tool 完成退款，并继续把执行结果反馈给 Agent。

系统包含数百个 Vue 3 业务组件，并由多个团队独立维护。模型供应商可能随时切换，Agent 输出可能出现字段缺失、非法组件名、Schema 版本不兼容、重复事件、乱序事件甚至恶意 Prompt Injection。

要求系统满足：

- 模型不能输出任意 HTML / JavaScript 并直接执行。
- 高风险操作必须重新鉴权，并支持 Human-in-the-loop。
- 流式生成过程中已经渲染的 UI 不能因后续错误导致整棵页面崩溃。
- 历史会话重新打开时，应尽可能稳定恢复当时的 UI。
- 组件升级不能导致历史 AI 消息大面积失效。
- 能够回答“某次生成为什么渲染成这个组件、为什么失败、用户点击后调用了哪个 Tool”。

请给出整体架构，并解释关键技术取舍。

## 核心考察点

- **Declarative UI Schema**：LLM 只生成声明式 UI AST / Schema，而不是 Vue SFC、HTML 或 JavaScript。
- **Component Registry**：通过受控 `componentType → renderer` 注册表暴露模型可使用的组件能力，区分展示组件与可执行组件。
- **Schema Validation**：使用 JSON Schema / Runtime Validator 校验模型输出，TypeScript 类型不能代替不可信边界上的运行时验证。
- **Protocol Versioning**：UI Schema、Component Contract、Tool Contract 独立版本化，并设计向前 / 向后兼容与 Migration。
- **Streaming UI**：将文本 Token 流与结构化 UI Event 流分离，避免用半截 JSON 驱动 Vue 渲染。
- **Vue 3 状态架构**：区分 Agent Run State、UI Document State、Component Local State 和 Server-authoritative Business State。
- **Command / Event Separation**：UI 描述“允许用户发起什么意图”，真正业务操作转换成受控 Command / Tool Call。
- **Security Boundary**：Prompt Injection 不应获得新的 Capability；所有 Tool 权限在可信服务端重新验证。
- **Failure Isolation**：单个动态组件 Schema 错误、组件加载失败或 Tool 超时不能污染整个 Chat / Workspace。
- **Observability**：关联 `runId → messageId → uiNodeId → interactionId → toolCallId → traceId`。

## 追问方向

1. 为什么不能让模型直接生成 Vue Template / JSX，然后通过动态编译渲染？即使放进 iframe 是否就足够安全？
2. 如果模型在 SSE 中先生成 `table`，随后不断追加 row，你如何设计事件协议避免每个 Token 都触发 Vue 深层响应式更新？
3. Component Registry 已升级到 v4，但两年前历史消息保存的是 v1 Schema，如何保证历史会话可恢复？
4. 一个 `RefundForm` UI 节点显示了“提交退款”按钮。用户点击后，前端是否可以直接根据 Schema 中的 `tool: refundOrder` 调用后端？为什么？
5. Prompt Injection 诱导模型生成管理员专属 `DeleteTenantButton`，系统应该在哪几层阻断？
6. SSE 断线重连后收到重复 `ui.patch` 事件，如何保证 UI Document 不重复应用 Patch？
7. 动态 UI 中某个组件导致 Vue 渲染异常或异步组件 Chunk 加载失败，如何做局部降级？
8. 如果多个 Agent 同时修改同一个 UI Document，你会使用 revision、optimistic concurrency、CRDT，还是其他方案？为什么？
9. 如何限制生成式 UI 对主线程、DOM 数量、网络请求和内存的消耗，避免模型生成“合法但昂贵”的 UI？
10. 如何建立指标判断 Generative UI 是否真的优于纯文本 Chat，而不是只增加系统复杂度？

## 参考答案要点

### 1. 把模型定位为 UI Planner，而不是代码生成执行器

推荐链路：

```
User Intent
    ↓
Agent / LLM
    ↓
Declarative UI Schema / UI Events
    ↓
Schema Validator + Policy Engine
    ↓
UI Document Store
    ↓
Component Registry
    ↓
Vue 3 Renderer
    ↓
User Interaction
    ↓
Command Gateway
    ↓
Authorization / Tool Runtime
```

模型只能选择平台显式暴露的 Capability。Schema 可以表达 `component: "order-table"`、props、data binding 和允许的 action intent，但不能包含 `eval`、任意函数、动态 import URL 或任意 DOM 脚本。

### 2. Schema 与组件实现解耦

不要把 Vue 组件文件名直接暴露给模型。建立稳定的领域组件 ID，例如 `commerce.order-table@2`。

Registry 保存组件 loader、props schema、支持的事件、Capability、资源预算和兼容版本。Vue 组件可以持续重构，而 AI 协议保持稳定。

对于大型应用，可将 Registry 分为 **Protocol Registry** 与 **Runtime Renderer Registry**：前者描述模型可见能力，后者映射到当前客户端实际实现。

### 3. 不可信输出必须 Runtime Validate

LLM 输出属于外部输入。TypeScript 的 `UIBlock` 接口在运行时不存在，不能证明收到的数据合法。

验证至少包括：结构 Schema、组件是否在 Allowlist、props 类型与长度、节点数量 / 深度、action 是否属于该组件声明能力、URL / 富文本策略以及当前用户是否有资格看到对应 Capability。

校验失败应生成受控 `unsupported/error` 节点，而不是让异常进入 Vue Renderer。

### 4. 使用结构化事件，而不是解析半截 JSON

建议 SSE / WebSocket 传输语义事件：

```
run.started
message.delta
ui.document.created
ui.node.added
ui.node.patched
ui.node.removed
ui.commit
interaction.accepted
tool.started
tool.completed
run.completed
```

每个事件携带 `eventId`、`seq`、`runId`、`documentId`、`revision`。客户端按 sequence 检测 gap，以 eventId 去重，并只在可提交边界更新 UI Document。

高频 row / token 数据可以先进入非深响应式 buffer，再按 animation frame 或批次提交到 Vue 状态，避免 reactive fan-out。

### 5. Vue 3 中不要建立一个巨大的 reactive AI 对象

建议分层：

- **Run Store**：连接、阶段、sequence、取消、重连状态。
- **UI Document Store**：规范化 node map、revision、parent-child relationship。
- **Domain Store**：订单、用户、权限等服务端事实。
- **Local Component State**：输入框焦点、展开状态等纯 UI 状态。

大型 immutable Schema 可使用 `shallowRef` / `markRaw` 等方式控制代理成本；通过 node-level selector / computed 限制更新传播范围，而不是每次 Patch 替换整个深层响应式树。

### 6. UI Action 不是 Tool Execution Authority

Schema 中即使存在 `action: "refund-order"`，它也只能代表交互意图。

点击后应形成带 `interactionId` 的 Command，经可信服务端重新进行身份、租户、资源权限、参数、额度、幂等和风险策略检查。高风险操作进入确认 / 审批流程。

因此安全原则是：**模型可以建议 Capability，但不能授予 Capability；前端可以表达 Intent，但不能决定 Authorization。**

### 7. Prompt Injection 必须按 Capability 模型治理

不要尝试只靠 Prompt 告诉模型“不要生成危险按钮”。即使模型被注入，攻击者也只能在已经授予该 Run 的 Capability 集合内活动。

推荐多层控制：Agent 可见 Tool 白名单 → UI Schema Allowlist → 前端 Capability Projection → Command Gateway → 服务端 Authorization / Policy → Tool 自身业务校验。

客户端隐藏按钮只是 UX，不是安全边界。

### 8. 历史恢复依赖协议版本，而不是当前组件代码

持久化的是规范化 UI Document + Schema Version + Component Contract Version + 必要的数据 Snapshot / Reference，而不是序列化 Vue Component Instance。

组件 Registry 应维护兼容 Renderer 或 Migration，例如 `order-table@1 → @2 → @3`。无法迁移时降级为稳定的只读表示 / Markdown Snapshot，而不是让历史消息完全打不开。

### 9. Failure Boundary 与资源预算必须是一等能力

每个动态节点建立 Error Boundary / Async Component fallback。单节点加载失败只替换该节点，不影响整个消息。

同时限制：最大 node 数、树深度、表格 row 数、并发异步组件加载数、组件网络请求预算、图片 / iframe 策略、单次 Patch 大小以及每个 Run 的 UI Mutation Rate。

这解决的是 **合法 Schema 造成的资源耗尽**，不仅是非法输入问题。

### 10. 建立端到端可观测链路

每次模型 UI 决策和用户交互都需要稳定 ID：

```
runId
 └─ messageId
     └─ documentId
         └─ uiNodeId
             └─ interactionId
                 └─ commandId
                     └─ toolCallId
                         └─ traceId
```

指标除了错误率，还应覆盖 Schema validation failure、unsupported component、UI first meaningful render、Patch latency、interaction → tool latency、恢复成功率、用户放弃率、人工修正率、Token / Tool / UI rendering 成本。

## 架构师级回答的关键判断

优秀回答不应停留在“让 LLM 返回 JSON，然后 Vue 动态组件渲染”。真正需要解决的是 **不可信、非确定性的模型输出如何进入一个确定性、可版本化、可授权、可恢复、可观测且具有资源边界的 UI Runtime**。

一个成熟方案的核心不变量应是：**LLM 决定意图和候选 UI；Protocol 定义可表达范围；Registry 定义可渲染能力；Policy 决定可用能力；Server 决定业务授权；Vue 3 只负责可靠地投影经过验证的 UI Document。**
