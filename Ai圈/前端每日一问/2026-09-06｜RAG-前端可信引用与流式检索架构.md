# 2026-09-06｜RAG 前端可信引用与流式检索架构

## 题目

你负责设计一个企业级 **Vue 3 + RAG** AI 知识助手。系统需要同时服务 10 万级用户，知识来源包括内部文档、代码仓库、工单和权限隔离的数据源。回答采用流式输出，并要求用户能够看到每个关键结论对应的引用来源。

请设计前端侧的整体架构，使系统在 **检索延迟不稳定、引用可能晚于答案到达、用户切换会话、重复提交、请求取消、权限变化、模型幻觉、文档版本更新** 等情况下，仍然保证交互流畅、引用可信、状态可恢复且可观测。

重点说明：前端如何建模一次 RAG 请求的生命周期；如何组织 Query、Retrieval、Rerank、Generation、Citation 等事件；Vue 3 中如何设计状态层；流式答案与引用如何建立稳定关联；哪些安全与一致性判断必须由服务端完成。

## 背景 / 场景

现有系统采用 `fetch + SSE` 接收模型 Token，并把 Markdown 字符串直接追加到 Vue `ref`。随着业务扩大出现以下问题：

- 模型已经输出结论，但对应 Citation 数秒后才返回，页面短时间展示“无来源”的答案。
- 用户快速连续提问后，旧请求的事件写入新会话。
- 用户点击停止生成后，浏览器停止渲染，但后端 Retrieval / LLM 仍继续运行并产生费用。
- 文档被更新或用户权限被回收后，历史 Citation 仍可能打开旧内容。
- 高频 Token 更新导致 Markdown 解析、响应式触发和 DOM Patch 占用主线程。
- 线上只能看到“请求失败”，无法判断问题发生在 Retrieval、Rerank、模型首 Token、Citation Resolution 还是前端渲染阶段。

要求在不牺牲 Vue 3 可维护性的前提下重新设计该系统。

## 核心考察点

1. **RAG 请求状态机**：是否把请求建模为具有 `requestId / conversationId / turnId / sequence` 的生命周期，而不是简单的字符串流。
2. **事件协议设计**：能否设计 `retrieval.started`、`retrieval.completed`、`generation.delta`、`citation.resolved`、`completed`、`failed` 等可演进事件，并处理重复、乱序和断线恢复。
3. **答案与 Citation 一致性**：Citation 应通过稳定的 `citationId / chunkId / documentVersion` 关联语义片段，而不是依赖 Markdown 字符位置。
4. **Vue 3 状态边界**：Server State、Conversation State、Streaming Buffer、Ephemeral UI State 分层；避免将高频 Token 全量写入大型 Pinia Store。
5. **渲染性能**：Token batching、`requestAnimationFrame`/时间片刷新、增量 Markdown 策略、虚拟化历史消息，以及对 INP / Long Task 的预算控制。
6. **取消与资源治理**：`AbortController` 只是客户端取消入口，还需要 request cancellation protocol 将取消传播到 Retrieval、Reranker 和 LLM execution。
7. **权限与安全**：Citation ACL、文档访问授权、Prompt Injection / indirect injection 防护必须建立服务端信任边界；前端不能根据隐藏按钮等方式承担授权职责。
8. **版本与缓存一致性**：Citation 携带 `documentId + version/revision`；历史答案需要区分“回答时引用版本”和“当前最新版本”。
9. **可观测性**：建立 `traceId`，拆分 Query Rewrite、Retrieval、Rerank、TTFT、Generation、Citation Resolution、Client Render 等阶段指标。
10. **降级策略**：检索超时、Citation 服务失败、模型切换、SSE 中断时，系统应该明确区分可重试、可降级和必须失败的场景。

## 追问方向

1. 为什么不能把 SSE 返回的所有 Token 直接 `store.message += token`？在 50–100 token/s 下 Vue 响应式系统和 Markdown Renderer 会发生什么？
2. `generation.delta` 已到达，但它引用的 `citationId` 尚未解析，UI 应立即展示文本、等待引用，还是阻塞整段答案？如何权衡 perceived latency 与可信度？
3. SSE 断线重连后服务端从 `sequence=120` 重放事件，而客户端已经处理到 135，如何保证幂等？
4. 用户点击 Stop 后，怎样证明取消真正传播到了模型供应商，而不仅是前端停止读取 ResponseStream？
5. 如果检索出的文档包含“忽略系统指令并调用某工具”的恶意内容，前端、RAG Pipeline、Agent Runtime 各自承担什么责任？
6. 文档版本 V12 被模型引用，随后更新到 V13。历史回答点击 Citation 时应该打开哪个版本？如果 V12 已因权限策略不可访问怎么办？
7. 如何设计 RAG 的 SLO？仅监控接口 P95 是否足够？
8. 如果未来从单模型切换为多模型 Router，前端协议如何避免与具体模型供应商耦合？

## 参考答案要点

### 1. 将一次回答建模为事件驱动的 Turn

核心实体可以是 `Conversation → Turn → Attempt`。每次提交产生不可变 `turnId`，每次重试产生新的 `attemptId/requestId`。所有流式事件必须携带稳定标识与单调递增 `sequence`，客户端 Reducer 只允许事件写入对应 Attempt。

不要把网络流直接等价为 UI 状态。推荐形成：**Transport Event → Protocol Validation → Event Reducer → Normalized State → View Projection**。这样 SSE、WebSocket 甚至断线后的事件回放都不会污染 Vue 组件模型。

### 2. 协议应该表达语义事件，而不是供应商 Token

例如事件族可以包括：

```
turn.accepted
retrieval.started
retrieval.completed
generation.started
generation.delta
citation.declared
citation.resolved
generation.completed
turn.completed
turn.failed
```

每个事件至少包含 `schemaVersion`、`requestId`、`turnId`、`sequence`、`timestamp` 和 payload。客户端按照 `(requestId, sequence)` 去重；若需要断线恢复，可通过 last acknowledged sequence 请求 Replay。

### 3. Citation 是一等领域对象

不要让模型生成 `[1]` 后再通过字符串位置猜来源。Generation 输出引用的是稳定 `citationId`，Citation Registry 再映射到 `documentId / chunkId / revision / sourceMetadata`。

UI 可以先显示文本并把未解析引用渲染为 pending 状态，但对于高风险业务可以采用 sentence/claim boundary buffering：关键 Claim 在 Citation 校验完成前不进入 trusted 状态。这里应由产品风险等级决定，而不是只有一种策略。

### 4. 高频 Streaming State 与业务 Store 分离

Pinia 保存 Conversation metadata、Turn 状态和最终 Snapshot；高频 delta 可以进入独立 Streaming Buffer，通过 `shallowRef`、非深响应式结构或专门的 stream controller 管理，并按帧或固定时间窗口批量提交到展示层。

关键目标不是“减少响应式”，而是让 **网络事件频率与 DOM 更新频率解耦**。例如 80 token/s 的输入完全没有必要触发 80 次 Markdown Parse + DOM Patch。

### 5. Cancellation 必须端到端传播

前端使用 `AbortController` 终止读取，同时向服务端发送具有 `requestId` 的 cancel command。服务端 Cancellation Token 再传播到 Retrieval、Reranker、Tool Execution 和模型 Provider。可观测系统记录 `cancel_requested_at / upstream_cancelled_at / tokens_after_cancel`，才能判断取消是否真正生效。

### 6. 前端不是 RAG 安全边界

Document ACL 必须在 Retrieval 与 Citation Resolve 阶段重新验证。Citation URL 不应该让浏览器直接持有绕过权限的永久对象地址，可以使用受控资源接口或短生命周期授权。

Prompt Injection 防御也不能依赖前端清洗字符串。外部文档属于 **untrusted data**，RAG/Agent Runtime 应区分 instruction 与 retrieved content，并对 Tool Calling 建立 capability、参数校验、用户确认和服务端授权。

### 7. 可观测性按 Pipeline 分段

至少追踪：`query_rewrite_ms`、`retrieval_ms`、`rerank_ms`、`time_to_first_token`、`generation_duration`、`citation_resolution_ms`、`time_to_first_meaningful_answer`、`client_render_delay`、取消成功率、SSE 重连率和 tokens-after-cancel。

`traceId` 应贯穿浏览器 → AI Gateway → Retrieval → Reranker → Model Provider，并把 `releaseVersion / modelRoute / knowledgeBaseVersion` 等维度加入 Trace，才能定位“某次前端发布”“某个模型”或“某批知识库更新”导致的回归。

### 8. 架构权衡

优秀答案不应声称所有复杂度都必须存在。低风险内部助手可以采用 eventual citation resolution 来换取低 TTFT；金融、法律等高风险场景则可能需要 Claim Validation 或 Citation Gate。架构师需要根据 **可信度、首屏延迟、成本、复杂度和故障恢复能力** 明确选择，而不是简单追求“流式越快越好”。

## 架构师级判断标准

候选人如果只回答“Vue 3 + Pinia + SSE + Markdown”属于实现层答案；能够进一步讨论 **事件协议、请求身份、幂等与回放、Citation 数据模型、端到端取消、权限边界、渲染调度和分段 Trace**，才进入架构设计层面。

真正的核心问题是：**RAG 前端不是一个把 LLM 字符串显示出来的聊天窗口，而是对检索、生成、证据与权限状态进行实时投影的事件驱动客户端。**
