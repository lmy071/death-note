# 2026-09-07｜Vue 3 多模型路由与降级治理

## 题目

你负责一个企业级 Vue 3 AI 工作台。系统同时接入多个云端 LLM 与一个浏览器端轻量模型，不同能力在质量、首 Token 延迟、吞吐、上下文窗口、Tool Calling 支持和调用成本上差异明显。

请设计一套**前端可感知但不与具体模型耦合的多模型路由与降级架构**：当主模型限流、超时、流式响应中断、工具调用能力不可用、成本预算超限或用户网络恶化时，系统应如何切换模型、恢复会话并保证 UI 状态一致？说明哪些决策应该放在前端，哪些必须由服务端 AI Gateway 控制，并给出可观测性、安全、协议演进与灰度治理方案。

## 背景 / 场景

某大型企业内部 AI 工作台基于 Vue 3 + TypeScript，提供聊天、知识库问答、代码生成和 Agent 工具调用。峰值并发较高，同时接入模型 A、模型 B、低成本模型 C，以及可选的浏览器端本地模型。

线上出现以下问题：

- 模型 A 在高峰期频繁触发限流，前端直接重试造成请求风暴。
- 流式回答已经输出一半后模型失败，简单切换模型会导致回答重复或语义断裂。
- 不同模型 Tool Calling Schema 和能力并不完全一致。
- 用户切换模型后，历史上下文 Token 数超过新模型窗口。
- Pinia 中直接保存 provider/model 字段，业务组件大量出现模型判断逻辑。
- 某模型质量下降，但平均延迟和 HTTP 成功率仍正常，传统监控无法快速发现。
- 降级到低成本模型后费用下降，但复杂任务成功率明显降低。

要求系统支持模型独立发布、灰度、熔断和快速回滚，同时避免模型供应商差异渗透到 Vue 组件层。

## 核心考察点

- **AI Gateway 与前端职责边界**：鉴权、密钥、供应商选择、配额、成本策略、熔断等应由服务端统一治理；前端负责能力表达、用户意图、交互状态与可解释的降级反馈。
- **Capability-based Routing**：业务不直接依赖模型名称，而声明 `requiredCapabilities`，例如 vision、toolCalling、structuredOutput、longContext、localInference。
- **统一请求/事件协议**：将供应商差异归一化为稳定的 Conversation / Run / Message / ToolCall / Usage 事件模型。
- **状态机设计**：区分 queued、routing、streaming、tool_waiting、recovering、completed、failed、cancelled，避免用多个 boolean 拼接状态。
- **流式故障恢复**：讨论 continuation、checkpoint、重新生成、答案分段以及何时不能透明切换模型。
- **上下文预算**：Token Budget、摘要压缩、检索上下文裁剪、历史消息分层以及模型切换后的窗口重新计算。
- **熔断与重试**：指数退避、jitter、Retry Budget、Circuit Breaker、Bulkhead，避免客户端无限重试形成放大效应。
- **成本与质量联合路由**：不能只按价格或延迟选择模型，应结合任务类型、SLO、质量评分和预算。
- **Vue 3 架构边界**：Composition API / Store 只消费稳定领域模型，不在组件中出现大量 `if (model === ...)`。
- **可观测性**：TTFT、TPS、E2E Latency、fallback rate、tool success rate、token usage、cost、cancel rate、quality signal，并建立 Run Trace。
- **安全治理**：API Key 不下发浏览器；本地模型与云模型的数据边界、敏感数据策略和 Tool 权限不能因 fallback 被绕过。
- **灰度与回滚**：Routing Policy、Prompt、Model Version、Tool Schema 应具有独立版本，并可关联到一次 Run。

## 追问方向

1. 主模型已经输出 800 个 Token 后连接断开，你会直接把剩余上下文交给备用模型继续生成吗？如何避免重复、风格突变和事实冲突？
2. 如果模型 A 的 HTTP 成功率是 99.9%，但 Agent 任务成功率从 92% 降到 65%，自动熔断系统如何发现？
3. 用户手动指定“必须使用模型 A”时，平台的自动降级策略是否还应该生效？产品语义如何设计？
4. 模型切换后上下文窗口从 128K 降到 32K，如何决定删除、摘要或重新检索哪些信息？
5. Tool Calling 参数 Schema 在不同供应商之间不兼容，应该由前端、Gateway 还是 Tool Adapter 负责转换？
6. 浏览器端本地模型作为 fallback 时，如何判断设备是否具备足够内存/GPU 能力？如何避免推理阻塞 Vue 主线程？
7. 如何防止某个页面的批量 AI 请求耗尽全局模型配额，影响其他业务？
8. 如何设计一次完整 Trace，使你能回答“这个回答为什么最终由模型 C 生成”？

## 参考答案要点

### 1. 建立稳定的 AI Domain Layer

组件层不直接认识供应商。业务提交的是任务意图，例如 `taskType`、`requiredCapabilities`、`latencyClass`、`qualityClass`、`privacyClass` 和预算约束。AI Gateway 根据 Routing Policy 将任务映射到具体模型。

前端只应获得必要的展示信息，例如当前运行阶段、是否发生降级、能力限制以及用户是否允许手动选择模型。这样新增或替换供应商时，不需要修改大量 Vue 组件。

### 2. 用 Capability Matrix 代替 Model Matrix

维护模型能力注册表，但业务代码查询的是能力而不是模型名。路由前先做硬约束过滤，再在候选模型中根据质量、成本、延迟、健康度进行评分。

典型流程可以抽象为：

`Intent → Capability Filter → Policy → Health/Quota → Scoring → Model → Adapter`

其中 Tool Schema 的供应商适配应位于 Gateway / Model Adapter 层，领域 Tool Contract 应保持稳定。

### 3. 将一次 AI 请求建模为 Run

为每次执行生成稳定 `runId`，模型切换产生新的 `attemptId`。事件携带单调递增序号，使前端能够处理重复、乱序与断线恢复。

前端 Store 保存规范化实体和 Run 状态，而不是把不断增长的完整 Token 字符串作为大量深层响应式对象更新。高频 Token 可以先进入非响应式 buffer，再按 animation frame 或固定时间窗口批量提交 UI。

### 4. Fallback 不是简单重试

在首 Token 前失败，可以相对安全地重新路由；已经流式输出后则必须根据任务语义决定策略。

可以保存 semantic checkpoint，例如已确认段落、Tool Result、结构化输出阶段。备用模型获得“已完成内容 + 剩余目标”，而不是简单复制最后几个 Token。无法保证 continuation 质量时，应显式重新生成，并让 UI 告知用户，而不是伪装成无缝续写。

### 5. 服务端统一治理重试和熔断

429、5xx、超时等模型级故障由 Gateway 执行有限重试、指数退避和 Circuit Breaker；浏览器不应对供应商接口进行无限重试。

需要同时设置 Retry Budget 和 Bulkhead：一个模型故障时，fallback 流量不能瞬间把第二个模型击穿。队列、并发限制和租户级配额共同控制故障扩散。

### 6. 路由指标必须包含“语义成功率”

HTTP 200 并不代表 AI 请求成功。Agent 场景至少还需要 Tool Call 成功率、任务完成率、结构化输出校验失败率、用户重试/重写率，以及离线评测或抽样 Judge 指标。

因此熔断可以分为基础设施熔断和质量熔断。后者应采用较长窗口、最小样本量和人工兜底，避免短期噪声造成频繁模型震荡。

### 7. 上下文必须重新预算

模型切换时重新执行 Context Planner，而不是直接复制原 Prompt。可以把上下文分成 System Policy、Recent Turns、Long-term Summary、Retrieved Evidence、Tool State 等层级，并为每类设置优先级和 Token Budget。

裁剪过程必须可追踪，否则模型切换后的质量下降无法解释。

### 8. Vue 3 只消费领域状态

建议将 AI 能力封装为 `useAIRun()`、`useConversation()` 等 composable，底层通过 service/repository 连接 Gateway。Pinia 负责可共享的会话领域状态，而 Token buffer、AbortController、ReadableStream reader 等生命周期对象不必全部进入深响应式 Store。

组件只渲染诸如 `run.phase`、`message.content`、`fallbackReason` 和 capability 状态，不承担路由算法。

### 9. 本地模型是另一种执行环境，而非普通 provider

浏览器端模型需要额外考虑 WebGPU 可用性、模型下载缓存、显存/内存、Worker 隔离、电量和设备温度等资源约束。应先进行 Device Capability Probe，再决定是否加入候选执行器。

涉及敏感数据时，本地推理可以成为隐私策略的一部分，但本地 fallback 不能因此绕过 Tool 权限、审计或企业安全策略。

### 10. 建立端到端 Run Trace

一次 Run 至少关联：`conversationId → runId → attemptId → routingPolicyVersion → model/provider/version → promptVersion → contextPlanVersion → toolSchemaVersion → token/cost → fallbackReason → outcome`。

这样才能同时支持故障定位、质量回归分析、成本归因和灰度回滚。

> **架构师级回答的关键**：不要把多模型能力设计成一个“模型下拉框”。真正的问题是建立一个具有稳定领域协议、能力发现、策略路由、故障隔离、上下文重规划、质量反馈和可观测性的 AI Runtime；Vue 3 前端只是这个 Runtime 的状态投影与交互入口。
