# 2026-09-01｜AI Agent流式状态机架构

## 题目

你正在为一个大型企业级 Vue 3 应用设计 AI Agent 工作台。用户发送请求后，Agent 可能连续执行 10～50 个步骤，包括模型推理、Tool Calling、人工确认、文件处理、代码执行与多个子 Agent 协作；服务端通过 SSE 持续返回事件。一次任务可能运行数分钟，用户可以取消、刷新页面、切换路由甚至重新打开浏览器后继续查看任务。

请设计前端架构，使系统能够正确处理 **流式事件、Agent 状态、并发任务、取消与重连、乱序/重复事件、工具审批、长任务恢复、Vue 3 渲染性能、协议演进、安全边界以及端到端可观测性**。说明你会如何划分 UI State、Agent Runtime State 与 Server State，以及为什么不能简单地把 SSE 收到的数据不断 append 到 Pinia 数组中。

## 背景 / 场景

系统同时存在以下约束：

- 单个 Agent Run 可能产生数千条 Token Delta 和数百条结构化事件。
- Tool Calling 可能暂停任务，等待用户审批后继续执行。
- 网络抖动后 SSE 会重连，服务端可能重新发送部分事件。
- 同一用户可以同时运行多个 Agent，且可以从多个浏览器标签页查看同一 Run。
- 前端和后端可能处于不同发布版本，事件协议需要向前/向后兼容。
- 某些 Tool Result 包含敏感数据，不允许未经处理直接进入日志或前端持久化层。
- Vue 3 页面需要持续渲染流式 Markdown，但不能因为高频 Token 更新导致主线程长任务和输入卡顿。

## 核心考察点

- 是否把 Agent Run 建模为显式状态机，而不是由多个 boolean 隐式组合状态。
- SSE Event 是否具有 `runId`、`eventId/sequence`、`type`、`schemaVersion`、`timestamp` 等可恢复协议字段。
- 如何处理 at-least-once delivery 下的重复、乱序、缺失事件与重放。
- Snapshot + Event Log 如何结合，避免刷新页面后必须重放数万条事件才能恢复状态。
- Token Delta 与结构化 Domain Event 是否分层处理，避免把传输层事件直接等价为 UI 状态。
- Vue 3 中如何控制高频响应式更新，例如批处理、requestAnimationFrame 调度、非响应式缓冲区、shallowRef、虚拟列表和 Markdown 增量渲染。
- `AbortController` 的取消语义如何与服务端真正终止 Agent Run 区分。
- Tool Approval 如何设计成服务端可验证的状态迁移，而不是只依赖前端按钮状态。
- 多标签页观察同一 Run 时，如何保证状态一致并避免重复连接/重复操作。
- 如何对 Prompt、Tool Arguments、Tool Result、模型输出建立安全与脱敏边界。
- 如何建立从用户操作 → Run → Model Call → Tool Call → 前端 Event Consumption 的 Trace。

## 追问方向

1. SSE 连接断开 20 秒后恢复，你如何判断这 20 秒内是否丢事件？如果服务端只保证至少一次投递怎么办？
2. `AbortController.abort()` 已经执行，但服务端 Agent 仍在调用付费模型，这属于什么架构问题？如何解决？
3. 为什么不建议每收到一个 Token 就直接修改 Vue 3 的响应式字符串？你会怎样把 100 次/秒的 Token 更新控制到合理的渲染频率？
4. Tool Call 进入 `awaiting_approval` 后，两个浏览器标签页同时点击“允许执行”，如何保证工具只执行一次？
5. Agent 协议从 v2 增加 `sub_agent_started` 事件，而旧前端只理解 v1，你会如何设计兼容策略？
6. 页面刷新后，是重放完整 Event Log、读取 Snapshot，还是重新请求最终消息？三种方式分别适合什么场景？
7. 如何区分“用户取消”“网络连接断开”“模型超时”“Tool 执行失败”和“Agent 被平台熔断”，使 UI 能给出正确的恢复动作？
8. 如果一个 Run 产生 50,000 个流式事件，哪些数据应该长期保存，哪些只应该用于瞬时渲染？

## 参考答案要点

### 1. 将 Agent Run 建模为显式状态机

不要使用 `isLoading + isStreaming + isToolCalling + isError` 这类 boolean 组合。Run 应有明确状态，例如 `queued → running → awaiting_approval → running → completed / failed / cancelled`，并定义合法迁移。Tool Call、Model Call、Sub Agent 可以拥有自己的子状态机。

状态迁移的权威来源应是服务端，前端负责 projection，而不是自行推断任务已经完成。

### 2. 建立稳定的事件协议

SSE 只是传输机制，真正需要治理的是 Event Protocol。每个事件至少应包含 Run 身份、单调递增 sequence 或唯一 eventId、事件类型、Schema Version 与时间信息。

客户端维护 `lastAppliedSequence`，对重复事件做幂等处理；发现 sequence gap 时主动请求缺失区间或重新获取 Snapshot，而不是继续展示可能已经失真的状态。

### 3. Event Log 与 Snapshot 分离

Event Log 适合审计、重放和调试，但不适合作为每次页面恢复的唯一数据源。服务端应周期性生成 Run Snapshot，并记录对应的 sequence watermark。

恢复流程可以是：读取最新 Snapshot → 从 watermark 之后补增量事件 → 建立 SSE 连接。这样恢复成本与 Run 总历史长度解耦。

### 4. Transport State、Domain State、UI State 分层

SSE 原始事件先进入非 UI 的 ingestion layer，完成校验、去重、排序和协议升级，再投影为 Agent Domain State。Vue 组件消费的是适合渲染的 View Model。

Pinia 可以承载可观察的领域投影，但不应该成为原始 Event Log、Token Buffer 和网络连接生命周期的混合容器。

### 5. 高频 Token 使用缓冲与批处理

Token Delta 可以先进入普通内存 Buffer，在 `requestAnimationFrame` 或 30～60ms 时间窗口内合并后一次提交给 Vue 响应式层。历史消息采用虚拟列表；已完成消息可以冻结或使用 `markRaw` / `shallowRef` 降低深层代理成本。

Markdown 渲染也应批处理，避免每个 Token 都重新解析完整 Markdown AST。必要时将解析工作移入 Worker，并对超长输出实施截断或分段加载。

### 6. 取消需要端到端语义

浏览器 `AbortController` 只能终止客户端 fetch/SSE 消费，并不能保证服务端计算停止。真正的取消应拥有服务端 `cancelRun(runId, expectedVersion)` 能力，由 Agent Orchestrator 传播 Cancellation Token 到 Model Call、Tool Call 与子 Agent。

取消操作本身应幂等，并最终由服务端发送 `run_cancelled` 确认。

### 7. Tool Approval 使用并发控制

审批是业务状态迁移，不能只在前端禁用按钮。请求应携带 Tool Call ID 和期望版本，例如 `approve(toolCallId, expectedVersion)`；服务端通过 CAS / optimistic concurrency 或唯一执行约束保证只有一个审批成功。

对于高风险工具，还应把工具名称、参数摘要、权限范围和副作用明确展示给用户，并由服务端再次做授权校验。

### 8. 多标签页与重连

多标签页可以通过 BroadcastChannel 共享 Run 更新，必要时选举一个标签页维护实时连接；但 Leader Election 只是连接优化，服务端幂等性仍然必须成立。

重连应携带 `Last-Event-ID` 或 sequence watermark。服务端无法补齐历史时，客户端应回退到 Snapshot Reconciliation，而不是假设连接恢复意味着状态完整。

### 9. 协议演进

事件 Envelope 与 Payload Schema 分开版本化。新增事件默认允许旧客户端忽略；破坏性字段变更通过新 Schema Version 或 Adapter 层处理。前端 ingestion layer 将不同服务端版本 normalize 成内部稳定模型，使组件不直接依赖 Wire Protocol。

### 10. 安全边界

Prompt、Tool Arguments、Tool Results 与模型输出均视为不可信输入。Tool Result 在进入日志、Telemetry、IndexedDB 或 Session Replay 前需要字段级脱敏策略；生成 Markdown/HTML 必须进行严格 Sanitization。

Tool Calling 的权限决策必须在服务端执行，不能因为模型生成了某个 Tool Call 就默认获得调用权限。

### 11. 可观测性

为一次 Run 建立统一 `traceId/runId`，串联用户提交、SSE 建连/重连、模型请求、首 Token 延迟、Token 吞吐、Tool Call、审批等待、取消传播和最终状态。

前端重点监控 TTFT、stream stall、sequence gap、重连次数、每秒响应式提交次数、Long Task、Markdown 渲染耗时与内存增长，并与后端模型/工具 Trace 关联。

## 面试官判断标准

优秀候选人应意识到：**AI Agent 前端不是一个“聊天框 + SSE”的问题，而是一个事件驱动、长生命周期、弱网络环境下的分布式状态投影系统。**

架构设计中应同时出现状态机、幂等、事件序列、Snapshot/Reconciliation、背压与渲染调度、端到端取消、协议版本、安全边界和可观测性。如果答案主要停留在 Pinia 保存消息、SSE 接收 Token、失败后重连，通常还没有达到前端架构师层面的系统设计深度。
