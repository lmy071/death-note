# 2026-08-29｜Vue 3 前端可观测性架构

## 题目

你负责一个大型 Vue 3 + TypeScript 前端平台，包含主应用、多个业务子应用、SSR 页面、CSR 页面和若干第三方 SDK。近期线上出现“用户偶发白屏、接口正常但交互卡死、某次发布后特定地区 LCP 恶化、微前端子应用加载失败”等问题，但现有监控只能看到 JS Error 和接口错误率。

请设计一套**面向大型前端系统的端到端可观测性架构**。要求能够从一次用户异常出发，关联到具体页面、Vue 组件、资源、接口链路、子应用版本和发布批次，并说明如何控制监控 SDK 自身的性能与成本。

## 背景 / 场景

平台由多个团队独立发布，存在灰度、A/B、CDN 多版本缓存以及微前端远程资源加载。部分问题不会产生 JavaScript 异常，例如 Long Task、主线程阻塞、Hydration 卡死、资源加载慢、无限响应式更新以及第三方脚本阻塞。

要求方案不仅回答“接入 Sentry”，而是建立统一的 telemetry 数据模型、上下文传播、采样、聚合、告警和故障定位体系。

## 核心考察点

- 前端 Observability 与传统 Error Monitoring 的边界
- Error、Performance、Resource、Network、User Action、Release 等信号如何统一建模
- Vue 3 `app.config.errorHandler`、`onErrorCaptured`、Unhandled Rejection 等异常边界设计
- Core Web Vitals、Long Task、Event Timing、Resource Timing、Navigation Timing 的采集策略
- Trace ID / Request ID 如何从浏览器传播到 BFF、网关和后端服务
- 微前端主应用与子应用如何统一 Session、Trace、Release、App Version 上下文
- Source Map 上传、版本绑定及生产环境源码安全
- Session Replay 的隐私、脱敏与采样策略
- 灰度发布下如何把异常率和性能回归关联到具体 Release
- 高流量场景下的动态采样、聚合、限流和成本治理
- 监控 SDK 自身的性能预算与故障隔离

## 追问方向

1. 一个页面没有任何 JS Error，但用户反馈“点击按钮后卡死 8 秒”，如何自动发现并定位？
2. Vue 3 出现响应式循环更新时，你希望采集哪些上下文，而不是仅记录错误堆栈？
3. 主应用版本 A 加载子应用版本 B，如何保证一条错误事件能够精确还原当时的版本组合？
4. 同一个错误一分钟产生 10 万次，客户端和服务端分别如何限流与聚合？
5. Source Map 是否应该部署到公网 CDN？如何既支持堆栈还原又避免源码泄漏？
6. 如何判断一次 LCP 恶化来自前端代码、图片 CDN、接口 TTFB，还是第三方脚本？
7. 用户操作轨迹应该记录到什么粒度？如何避免密码、Token、表单隐私数据进入监控系统？
8. 如果监控 SDK 自身异常或阻塞主线程，如何保证它不会扩大线上故障？

## 参考答案要点

### 1. 建立统一事件模型

不要让错误、性能、网络、行为日志成为互不关联的数据孤岛。所有 telemetry 至少携带 `sessionId`、`traceId`、`appId`、`release`、`route`、`environment`、`region`、`deviceClass`、`deploymentId` 等公共维度。微前端还应记录主应用与所有已加载子应用的版本映射。

### 2. 错误体系

Vue 3 层使用 `app.config.errorHandler` 捕获框架级异常，并结合组件名、路由、业务域和发布版本；同时覆盖 `window.onerror`、`unhandledrejection`、资源加载错误。组件局部容错可以使用 `onErrorCaptured`，但应明确哪些错误被消费、哪些继续上报，避免重复事件。

### 3. 性能不是只有 Web Vitals

Web Vitals 用于宏观体验指标，但架构级诊断还需要 Long Task、Event Timing、Resource Timing、Navigation Timing、自定义 Performance Mark/Measure。对于“点击后卡死”，应把用户交互事件与后续 Long Task、网络请求、Vue 更新周期和路由变化关联起来。

### 4. 分布式链路

浏览器生成或继承 Trace Context，请求经过 BFF / Gateway 后继续向下游传播。前端 span 应覆盖用户操作、路由切换、数据请求以及关键异步任务，使一次用户点击能够关联到后端 trace，而不是只依赖 URL 和时间戳人工碰撞。

### 5. 微前端上下文

主应用负责生成稳定的 session / trace 上下文，并通过明确的平台 SDK 向子应用注入。每次事件记录 `{shellRelease, subAppId, subAppRelease}`；同时维护当前页面已加载 remote manifest 的版本快照，避免仅记录主应用版本导致错误归因。

### 6. 发布关联

CI/CD 在构建阶段生成唯一 `releaseId`，上传 Source Map 和构建元数据；部署阶段生成 `deploymentId`。监控平台按版本计算 Error Rate、Crash-free Session、LCP/INP 等指标，并与上一稳定版本比较。灰度阶段出现显著回归时可以触发自动停止扩量或回滚。

### 7. Source Map 治理

生产 bundle 可以不公开 `.map` 文件。CI 将 Source Map 上传到受控监控平台，并以 release + artifact path 建立映射；上传完成后构建产物中移除 Source Map，既能还原生产堆栈，又降低源码公开风险。

### 8. 数据量与采样

错误事件不能简单随机采样：新错误、Fatal、核心链路应提高采样率；高频重复错误使用 fingerprint 聚合。性能数据可以按用户、路由、设备、地区动态采样。客户端先限频和批量发送，服务端再做去重、聚合与异常流量保护。

### 9. 隐私与 Replay

默认禁止采集密码、Token、Cookie、Authorization Header 和敏感表单字段。Replay 采用 DOM mask、字段 allowlist / denylist 与低比例采样；异常 Session 可提高保留概率，但仍必须遵守脱敏规则。

### 10. 监控 SDK 自身必须有性能预算

SDK 应异步初始化、批量发送、限制队列长度，避免同步序列化大型对象；上报失败不能阻塞业务请求。对 SDK 自身建立 CPU、内存、网络开销预算，并提供远程降级开关。当监控系统异常时，应优先丢弃 telemetry，而不是影响业务主流程。

## 面试官判断标准

优秀候选人应把可观测性视为大型前端架构的基础设施，而不是“安装一个错误监控 SDK”。回答应能够建立从 **用户行为 → 浏览器性能 → Vue 运行时 → 网络请求 → 后端 Trace → Release / Deployment** 的关联链路，并同时讨论采样成本、隐私、安全、版本治理以及监控系统自身的故障隔离。
