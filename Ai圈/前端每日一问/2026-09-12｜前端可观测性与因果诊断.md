# 2026-09-12｜前端可观测性与因果诊断

## 题目

你负责一个大型 Vue 3 SaaS 前端，采用微前端架构并同时运行多个业务子应用。近期线上出现一类非常棘手的问题：用户偶发反馈“点击保存后页面卡住 3～8 秒”，但后端接口 P95 只有 300ms；常规错误监控没有异常，实验室性能测试也无法稳定复现。

请你以**前端架构师**身份设计一套能够从“用户一次交互”出发，定位到具体网络请求、JavaScript 长任务、Vue 组件更新、状态变更和微前端边界的可观测性体系。要求它不仅能采集指标，还要能够回答“这次卡顿为什么发生”。

系统日活千万级，因此必须同时考虑 SDK 性能开销、采样、数据量、隐私、跨应用 Trace 传播和治理成本。

## 背景 / 场景

现有系统存在以下情况：

- Vue 3 + Composition API，多个团队独立维护业务模块。
- Pinia 中存在大型共享 Store，一次 mutation 可能触发大量 computed / watcher / component update。
- 微前端 Shell 与子应用独立发布。
- axios/fetch 请求经过统一 BFF，但浏览器侧没有统一 Trace Context。
- 已采集 JS Error、接口耗时、LCP/INP 等指标，但彼此无法关联。
- 用户卡顿可能来自 JSON Parse、大对象响应式转换、同步计算、第三方 SDK、微前端切换或 DOM 更新。
- 不能为了排障长期录制所有用户的完整 Session Replay。

## 核心考察点

1. **Telemetry 数据模型**：Metric、Log、Trace、Event、Profile 各自解决什么问题，为什么只看 Web Vitals 不够。
2. **Interaction-centric Trace**：如何把 pointer/click → handler → state mutation → network → parse → Vue update → paint 串成同一条因果链。
3. **Trace Context 传播**：Shell、微前端、Web Worker、BFF 之间如何传递 traceId / spanId / interactionId。
4. **Vue 3 可观测性边界**：如何观察组件更新、effect/watch/computed 开销，而不侵入每一个业务组件。
5. **主线程诊断**：Long Task、Long Animation Frame、Event Timing、PerformanceObserver 如何组合使用。
6. **网络耗时拆解**：不能把 fetch resolve 当成“页面已经完成”，需要区分 network、body download、JSON parse、normalization、store commit、render。
7. **采样策略**：head sampling、tail sampling、异常动态升采样，以及如何避免千万 DAU 下的数据爆炸。
8. **微前端治理**：独立团队如何共享 Telemetry Contract，同时避免强耦合到某一个监控厂商 SDK。
9. **隐私与安全**：输入内容、URL、Prompt、Token、用户标识等字段如何脱敏与分级。
10. **SLO 与故障归因**：如何从“INP 变差”进一步定位到某版本、组件、Store mutation 或第三方脚本。

## 追问方向

### 追问 1：INP 很高，但所有接口都很快，下一步怎么查？

要求候选人区分输入延迟、事件处理时间、presentation delay，并进一步分析 Long Task、Vue 更新和 Layout/Paint。

### 追问 2：一次 Pinia mutation 导致 300 个组件更新，怎么找到根因？

不能只回答“使用 Vue DevTools”。需要考虑生产环境下的低开销 instrumentation、mutation correlation、组件聚合统计和采样。

### 追问 3：微前端 A 调用 Shell，再由 Shell 调用微前端 B，Trace 如何保持连续？

考察跨 runtime 的 context propagation，以及协议应该属于平台层还是具体业务 SDK。

### 追问 4：PerformanceObserver 本身会不会拖慢页面？

要求讨论 observer callback 批处理、buffer、数据聚合、采样、主线程预算和 SDK 自身性能指标。

### 追问 5：线上只有 0.1% 用户出现问题，普通 1% 随机采样可能仍抓不到怎么办？

考察 tail-based / trigger-based sampling：当检测到超阈值 INP、Long Task、异常请求链或用户主动反馈时，提高该 session / trace 后续采样率。

### 追问 6：第三方 SDK 阻塞了主线程，但它没有进入你们的业务 Trace，如何归因？

需要利用 Long Task / LoAF attribution、Resource Timing、script URL、版本信息，将非业务代码映射到 dependency ownership。

### 追问 7：如果用户点击“取消”，网络请求已经 abort，但页面仍然卡顿 2 秒，为什么？

考察 AbortController 只能取消部分异步工作；已经开始的 JSON parse、同步 normalization、响应式转换、watcher/effect 和渲染任务仍可能继续执行，因此需要完整的 cancellation propagation 和 stale-work suppression。

## 参考答案要点

### 1. 建立 Interaction 作为顶层诊断单元

不要以 API Request 作为前端 Trace 的根节点，而应以用户交互建立 Interaction Trace，例如：

`interaction.save-order`

下面关联：

`event-handler → store-action → http-request → response-download → json-parse → normalize → pinia-commit → vue-update → layout → paint`

这样才能回答“接口 300ms，为什么用户等了 5 秒”。

### 2. 建立统一 Telemetry Contract

平台层定义与监控厂商无关的接口，例如：

- startInteraction
- startSpan
- addEvent
- recordMetric
- reportError
- setAttribute

业务和微前端只能依赖该契约，不直接依赖具体 APM SDK。底层 Adapter 再映射到实际监控系统。

统一基础字段至少包含：

- traceId
- spanId
- interactionId
- sessionId（匿名化）
- appId / microAppId
- route
- buildId / releaseId
- component / feature
- device class
- network class

### 3. Vue 3 不应全量追踪每个 effect

生产环境对所有 reactive dependency 做完整追踪成本过高。

更合理的方式是分层：默认只采集 Interaction、Long Task、关键 Store Action、Route、Network 和高成本 Component Update；检测到异常 Trace 后，对命中的 session 或 feature 开启更高粒度采样。

对组件维度应优先记录聚合信息，例如某次 interaction 中：

- component update count
- total update duration
- max update duration
- top-N expensive components

而不是上传每次响应式 dependency tracking。

### 4. 网络必须拆成完整数据处理流水线

很多系统只记录：

`fetch start → fetch end`

但真正应该观察：

`DNS/TCP/TLS → TTFB → download → decode → JSON.parse → schema validation → normalization → state commit → render`

例如一个 20MB JSON 接口网络只需要 500ms，但 JSON.parse + 数据转换 + Vue reactive proxy 创建可能占用数秒主线程。

### 5. 将浏览器 Performance API 与业务 Trace 关联

通过 PerformanceObserver 观察：

- Event Timing
- Long Task / Long Animation Frame
- Navigation Timing
- Resource Timing
- Largest Contentful Paint
- Layout Shift

关键不是单独上报这些数据，而是将它们通过时间窗口和 interactionId 与业务 Trace 关联。

最终能够得到类似诊断：

> Save Interaction 4.8s，其中 API 286ms，JSON parse 740ms，Pinia normalization 1.2s，Vue component update 1.6s，Layout/Paint 630ms。
> 

这比“INP = 1800ms”更具有工程价值。

### 6. 微前端必须共享 Trace Context，而不是共享监控 SDK 实例

Shell 建立 interaction context；跨微前端通信协议携带 traceparent / interactionId。Web Worker、postMessage、事件总线以及 BFF 请求也应显式传播 Context。

各微前端可以独立发布，但必须遵守平台定义的 Telemetry Schema 与版本兼容策略。

### 7. 使用分层采样控制成本

建议组合：

- 低比例随机 baseline sampling；
- Error / INP / Long Task 超阈值强制保留；
- 新版本发布阶段提高采样；
- 特定 feature / tenant 灰度升采样；
- 异常 interaction 触发短时间 diagnostic mode；
- 服务端 tail sampling 决定完整 Trace 是否持久化。

高基数属性必须受治理，例如完整 URL、用户输入、动态 ID 不应直接作为 Metric label。

### 8. 建立 Ownership 与 Release Correlation

Telemetry 必须能回答：

`异常 → feature → microApp → package → release → owner`

Build Pipeline 在 artifact 中注入 buildId、Git revision、dependency manifest、source map version 等信息。

当某次发布后 INP P75 恶化时，可以自动关联到对应版本及负责团队，而不是依赖人工排查。

### 9. 可观测性 SDK 自己也必须有预算

架构师需要给 SDK 明确 Performance Budget，例如：

- 初始化耗时上限；
- bundle size 上限；
- 每分钟事件数量；
- observer callback CPU 时间；
- 内存 buffer 上限；
- 单 session 上传流量上限。

监控系统不能成为新的性能事故来源。

### 10. 最终目标是因果诊断，而不是 Dashboard 数量

成熟体系应该能够从一个异常指标反向钻取：

`INP Regression → Interaction → Long Task → Vue Update → Store Action → Feature → Release → Owner`

同时支持从一次用户投诉正向查看完整执行链。

架构设计的核心不是“接入哪个 APM”，而是建立统一的 **Interaction Model + Trace Context + Telemetry Contract + Sampling Policy + Ownership Model**，使性能、错误、网络、状态和发布信息能够形成同一套可查询的因果关系。
