# 2026-09-04｜浏览器端 AI 推理资源调度

# 题目

你负责设计一个大型 Vue 3 企业应用的新一代 AI 工作台。产品要求在浏览器端运行小型语言模型、Embedding 模型与部分视觉模型，用于敏感数据摘要、离线检索和低延迟补全；复杂任务仍可回退到云端模型。

请设计一套**浏览器端 AI 推理资源调度架构**：在 WebGPU 可用性、GPU/内存预算、多个 AI 任务并发、主线程交互性能、模型加载与缓存、设备差异、页面生命周期以及云端降级之间做出系统性权衡。要求说明前端如何避免 AI 推理拖垮页面，并使整个体系具备可维护性、可观测性和可演进性。

# 背景 / 场景

业务是一个长期运行的 Vue 3 SPA，包含文档编辑、搜索、数据分析和 AI Assistant。用户设备跨度很大，从高性能桌面设备到集成显卡笔记本。

系统同时可能发生：

- 用户输入时触发低延迟本地补全；
- 文档保存后批量生成 Embedding；
- AI Assistant 发起本地推理；
- 后台索引任务持续运行；
- 页面本身还有复杂 Vue 组件、图表和动画需要保持流畅。

线上出现过 GPU 内存快速增长、长任务导致输入卡顿、模型首次加载过慢、后台标签页恢复后任务集中爆发，以及部分设备 WebGPU 不稳定等问题。

# 核心考察点

- **能力探测与执行平面**：不要简单以 `navigator.gpu` 存在作为可用标准，应形成 Capability Profile，并将 WebGPU、WASM/CPU、云端推理抽象为不同 Execution Backend。
- **AI Scheduler**：将补全、Embedding、聊天推理、后台索引等任务统一建模，至少考虑 priority、deadline、estimatedCost、memoryBudget、cancelToken、foreground/background 等维度。
- **主线程隔离**：分析 Worker、Web Worker、OffscreenCanvas 等边界；明确哪些工作不能进入 Vue 渲染主线程，以及 Worker 并不自动解决 GPU/内存争用。
- **背压与抢占**：前台交互任务优先，后台 Embedding 必须限流；高优任务到达时需要暂停、取消或延迟低优任务，而不是无限堆积 Promise。
- **资源预算**：建立 GPU/CPU/内存/并发预算；讨论模型常驻、卸载、LRU、量化模型以及不同模型共享资源的策略。
- **模型生命周期**：Manifest、版本、分片下载、Cache Storage/IndexedDB、完整性校验、缓存淘汰和版本迁移。
- **Vue 3 响应式边界**：模型对象、Tensor、GPUBuffer 等重型对象不应深度 reactive；UI Store 保存任务投影和状态，而不是底层推理运行时对象。
- **页面生命周期治理**：处理 `visibilitychange`、冻结/恢复、AbortSignal、任务过期和恢复后的惊群问题。
- **本地 / 云端路由**：根据能力、隐私、延迟、成本、模型质量与错误率动态选择 Local / Cloud，而不是把降级写成散落的 `if`。
- **可观测性**：采集模型加载时间、TTFT、tokens/s、任务排队时间、推理耗时、取消率、OOM/Device Lost、主线程 Long Task、INP 影响及 Local→Cloud fallback 比例。

# 追问方向

1. WebGPU 可用但实际性能比 WASM 更差，或者频繁出现 Device Lost，你如何动态调整执行策略？
2. 用户正在输入，后台同时有 5000 个 Embedding 任务。如何保证输入、动画和 AI 补全的 P95 延迟？
3. 一个 1.5 GB 模型加载完成后导致浏览器标签页内存压力过高，你如何设计模型驻留与淘汰机制？
4. 页面进入后台 20 分钟后重新激活，积压任务如何恢复，为什么不能一次性重新执行？
5. 多个组件同时请求同一个模型时，如何避免重复初始化和重复占用 GPU 资源？
6. 本地推理失败后切换云端，如何保证请求幂等、UI 状态连续以及用户不会看到重复回答？
7. 如何验证 AI Scheduler 没有损害核心 Web Vitals？你会定义哪些 SLO？
8. 如果未来浏览器增加新的本地 AI API，怎样避免业务组件与 WebGPU/WASM 实现强耦合？

# 参考答案要点

## 1. 分层，而不是让组件直接调用模型

推荐拆分为：

```
Vue Components
      ↓
AI Application API
      ↓
AI Task Scheduler
      ↓
Policy / Capability Router
      ↓
┌──────────┬──────────┬──────────┐
│ WebGPU   │ WASM/CPU │ Cloud AI │
└──────────┴──────────┴──────────┘
      ↓
Model Runtime / Cache / Telemetry
```

业务组件只提交语义任务，例如 `autocomplete`、`embedding`、`chat`，不直接决定使用哪个模型或执行后端。这样才能集中治理设备适配、资源预算和降级策略。

## 2. Scheduler 是核心，而不是 Promise.all

任务应拥有结构化元数据，例如：

```tsx
interface AITask<TInput = unknown> {
  id: string
  type: 'autocomplete' | 'embedding' | 'chat' | 'indexing'
  priority: number
  deadline?: number
  estimatedMemory?: number
  input: TInput
  signal: AbortSignal
}
```

调度器需要提供有界队列、优先级、并发限制、deadline、取消、任务合并与背压。后台任务不能通过无限 `Promise.all` 抢占资源。

交互型补全通常应获得最高优先级；Embedding 可以批处理，并在浏览器空闲、设备资源允许时执行。

## 3. 将资源预算视为一等架构概念

不能只控制请求数量，还要控制 **模型驻留内存 + Tensor 中间结果 + GPU Buffer + JS Heap**。

可以维护 Model Pool：模型通过引用计数或 Lease 获取；长期未使用的模型进入可淘汰状态；发生内存压力、Device Lost 或高优模型加载时主动释放低优模型资源。

模型大小、量化等级和上下文窗口也可以作为调度策略的一部分。例如资源不足时从高精度模型降级到更小的量化模型，而不是直接让页面 OOM。

## 4. Vue 只维护 UI Projection

Vue/Pinia 中建议维护：任务状态、进度、结果摘要、错误、当前 Backend 等可序列化状态。

模型实例、GPUDevice、GPUBuffer、Tensor、Worker 通道等 Runtime Object 应放在独立 service/runtime 层，并使用 `markRaw`、`shallowRef` 或完全脱离 Vue 响应式系统，避免 Proxy 成本、错误生命周期和不可控引用链。

## 5. Local / Cloud 应是策略路由

建立统一 Policy Engine，例如综合：

```
privacy requirement
+ device capability
+ model availability
+ estimated latency
+ current queue pressure
+ failure history
+ network condition
+ cloud cost
→ execution backend
```

当某设备连续发生 WebGPU Device Lost 时，可以在当前 session 降低该 Backend 的健康评分并自动转向 WASM 或 Cloud，形成 circuit breaker，而不是每个组件各自重试。

## 6. 生命周期必须支持取消与过期

输入补全是典型的 stale task：用户继续输入后，旧任务即使完成也不应提交结果。

因此需要 `AbortController + generation/requestId` 双重控制：Abort 尽量停止底层计算，generation 防止无法真正取消的任务把旧结果写回 UI。

后台页面恢复时应重新计算任务价值和 deadline，丢弃过期任务，并通过 jitter + bounded concurrency 分批恢复，避免 thundering herd。

## 7. 可观测性必须关联到用户体验

AI 指标不能与前端性能指标割裂。建议把 `taskId / modelVersion / backend / deviceClass / releaseId` 注入统一 Trace。

至少观察：

- Queue Wait P50/P95/P99；
- TTFT 与 tokens/s；
- 模型下载、初始化和 warm-up 时间；
- GPU Device Lost / OOM；
- Local → WASM / Cloud fallback；
- Abort / stale result 比例；
- AI 任务运行期间的 INP、Long Task、掉帧情况。

可以定义类似 **“前台 AI 任务运行时 INP P75 不得显著劣化”** 的体验 SLO，而不只是关注模型 tokens/s。

## 8. 架构师级答案应体现的核心原则

最终方案应体现：**AI 推理属于共享且昂贵的浏览器资源，需要像操作系统调度 CPU 一样被集中治理。**

优秀答案不应停留在“Web Worker + WebGPU + IndexedDB”，而应进一步讨论资源所有权、任务优先级、背压、取消、模型生命周期、故障隔离、动态降级、Vue 响应式边界和用户体验 SLO。
