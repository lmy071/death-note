# 2026-08-28｜Vue 3 多标签页状态一致性架构

## 题目

你负责一个大型 Vue 3 + TypeScript 企业级工作台。用户经常同时打开 5～20 个浏览器标签页操作同一业务对象，例如订单、审批单或实时监控任务。系统目前使用 Pinia 管理客户端状态，并通过 WebSocket 接收服务端实时更新。

随着业务规模增长，线上开始出现以下问题：不同标签页状态不一致；用户在 A 页修改后 B 页仍展示旧数据；多个标签页同时刷新 Token、重连 WebSocket 或执行轮询造成服务端放大流量；离线恢复后旧状态覆盖新状态；不同版本前端同时存在时跨标签通信协议不兼容。

请设计一套可长期演进的 **Vue 3 多标签页状态一致性架构**。重点说明状态所有权、跨标签通信、冲突解决、Leader Election、实时连接复用、持久化、版本治理、故障恢复、性能与可观测性。

## 背景 / 场景

系统具有以下约束：

- Vue 3 + TypeScript + Pinia。
- 用户可能同时打开 5～20 个标签页。
- 核心业务数据通过 REST/GraphQL 获取，同时存在 WebSocket 实时推送。
- 页面可能运行不同部署版本，新版本灰度期间旧页面不会立即关闭。
- 部分用户会休眠电脑、断网后恢复，或者长期保持标签页不刷新。
- 业务数据要求最终一致，关键写操作必须避免旧数据覆盖新数据。

## 核心考察点

- 是否区分 **Server State、Client State、Session State、UI State**，而不是把所有状态都塞入 Pinia。
- 是否明确服务端才是业务事实源，跨标签同步不应演变为多个客户端副本之间互相覆盖。
- BroadcastChannel、SharedWorker、Service Worker、storage event 等方案的能力边界与兼容策略。
- Leader Election 如何避免多个标签页重复建立 WebSocket、刷新 Token 或执行轮询。
- 如何处理 split-brain、标签页冻结、Leader 崩溃以及浏览器后台节流。
- 如何通过 revision / version / ETag / updatedAt 等机制解决并发写入和旧数据覆盖。
- IndexedDB 等持久化数据恢复时如何避免 stale snapshot 污染最新状态。
- 不同前端版本之间的跨标签协议如何兼容和演进。
- 如何控制响应式对象规模，避免跨标签消息导致 Vue 3 大面积无效更新。
- 如何建立跨标签链路的日志、指标和故障定位能力。

## 追问方向

1. 为什么不建议直接把整个 Pinia Store 序列化后通过 BroadcastChannel 广播？
2. 如果 10 个标签页同时启动，如何保证最终只有一个 Leader？
3. Leader 所在标签页进入后台并被浏览器冻结 5 分钟，会发生什么？
4. 如果 A 标签页基于 revision=100 修改订单，而服务端已经是 revision=102，前端应该如何处理？
5. BroadcastChannel 消息是否需要 ACK？什么消息需要，什么消息不需要？
6. 新版本增加了事件字段，而旧标签页仍在线，协议如何做到向前/向后兼容？
7. WebSocket 应由 Leader 标签页持有还是放到 SharedWorker？如何选择？
8. IndexedDB 中缓存了昨天的数据，用户今天重新打开页面时如何判断缓存是否可信？
9. 如何避免一个标签页发送大量状态变化导致其他 19 个标签页同时产生昂贵的 Vue 响应式更新？
10. 什么情况下你会放弃客户端跨标签一致性，直接要求所有标签独立向服务端重新验证数据？

## 参考答案要点

### 1. 先定义状态所有权

第一原则是 **服务端业务数据是 Source of Truth**。Pinia 主要负责客户端视图状态和服务端数据的局部投影，而不是成为跨标签分布式数据库。

建议至少拆分为：

- Server State：订单、审批单等业务实体，以服务端 revision 为准。
- Session State：登录身份、租户、权限版本等，可跨标签协调。
- Client State：当前工作区配置等有限客户端状态。
- UI State：弹窗、展开状态、临时表单等默认不跨标签同步。

只有确实需要共享的状态才进入跨标签协议。

### 2. 同步事件，而不是同步整个 Store

不要广播 Pinia Snapshot。定义显式事件协议，例如：

```tsx
type CrossTabEvent =
  | {
      type: 'entity-invalidated'
      entity: 'order'
      id: string
      revision: number
    }
  | {
      type: 'session-updated'
      sessionVersion: number
    }
  | {
      type: 'leader-heartbeat'
      leaderId: string
      epoch: number
    }
```

消息表达“发生了什么”，接收方根据需要重新获取数据，而不是直接接受另一个标签页发送的任意状态。

### 3. BroadcastChannel 作为默认通信层

现代浏览器环境可优先使用 BroadcastChannel。对不支持的环境，可降级到 storage event 或完全取消跨标签优化。

协议必须包含至少：schemaVersion、messageId、senderId、timestamp/epoch，以及业务 Payload。接收方需要忽略自身消息、重复消息和无法识别的事件。

### 4. Leader Election

Leader 负责 WebSocket、Token Refresh、全局轮询等昂贵任务，Follower 通过 BroadcastChannel 接收事件。

Leader Election 不应只依赖一个 localStorage 布尔值。需要 Lease + Heartbeat：Leader 定期续租；Follower 发现 Lease 超时后竞争；竞争结果使用 epoch/fencing token 区分新旧 Leader。

即使出现短暂双 Leader，服务端和客户端也必须能够容忍，因此系统目标不是理论上的严格单主，而是 **可恢复且幂等**。

### 5. SharedWorker 是更强但有约束的方案

如果目标浏览器环境允许，SharedWorker 可以天然成为同源多个标签页共享的连接中心，把 WebSocket 生命周期从某个具体标签页中剥离出来。

但需要考虑浏览器兼容性、调试成本和生命周期语义。架构上应通过 Transport Adapter 隔离实现，使 BroadcastChannel + Leader 与 SharedWorker 可以替换，而不是让业务代码依赖具体 API。

### 6. 并发写入不能靠客户端广播解决

关键写操作应携带服务端版本，例如 revision 或 ETag：

```
PUT /orders/123
If-Match: "revision-100"
```

若服务端当前已经是 revision 102，应返回冲突，客户端重新拉取数据并让业务层决定自动合并、重试或提示用户。

跨标签事件只负责尽快让其他页面失效缓存，不能替代服务端并发控制。

### 7. 缓存采用 stale-while-revalidate 思路

IndexedDB Snapshot 应携带 schemaVersion、entityRevision、cachedAt 等元数据。页面启动时可以先展示允许过期的数据提升体验，但必须异步向服务端验证。

对于资金、权限、审批状态等关键数据，不应把本地缓存作为可信事实源。

### 8. Vue 3 响应式边界

不要让跨标签事件直接替换一个巨大的 reactive Store。实体数据应按 ID 分片，只有受影响实体更新。

大型不可变对象可以使用 shallowRef / shallowReactive；SDK、连接对象等非 UI 数据可 markRaw；事件应尽可能发送 ID + revision，而不是完整实体 Payload，从而减少 structured clone、GC 和 Vue dependency trigger 的成本。

### 9. 协议版本治理

跨标签协议本质上是一个分布式协议，因为灰度期间不同版本前端会同时运行。

建议采用可扩展 Envelope + schemaVersion。新增字段默认 optional；重大不兼容修改创建新事件类型或协议版本。未知事件必须安全忽略，不能导致旧标签页崩溃。

必要时新旧版本检测到协议不兼容后，可以主动退化为“独立连接 + 服务端重新验证”，优先保证正确性。

### 10. 可观测性

至少记录：tabId、leaderId、leaderEpoch、appVersion、protocolVersion、WebSocket connectionId、事件类型、消息延迟、Leader 切换次数、重复消息数量、冲突次数、缓存命中/失效次数。

线上排查时应能回答：某个用户当时有多少标签页、哪个标签是 Leader、收到什么 revision、何时发生 Leader 切换，以及最终为什么展示了某个版本的数据。

## 面试官判断标准

优秀候选人应认识到这是一个小型分布式系统问题，而不只是“用 BroadcastChannel 同步 Pinia”。答案应围绕 **事实源、协议、版本、租约、幂等、冲突检测、故障恢复和可观测性** 展开，并明确哪些一致性责任必须由服务端承担。

如果候选人能够进一步讨论 fencing token、浏览器冻结导致的租约误判、SharedWorker 生命周期、服务端乐观并发控制，以及不同前端版本并存时的协议兼容策略，可视为达到较强的前端架构师水平。
