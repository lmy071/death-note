# 2026-09-18｜BFCache生命周期与资源治理

## 题目

你负责一个大型 Vue 3 SaaS 平台，采用 SPA + 部分 SSR，包含 Pinia、WebSocket/SSE、轮询、Web Worker、BroadcastChannel、IndexedDB、本地缓存以及多个微前端。近期团队发现：用户从详情页跳转到外站再通过浏览器“后退”返回时，有时可以瞬间恢复，有时却整页重新加载；另一些页面恢复后出现 WebSocket 重复连接、轮询翻倍、旧权限状态继续显示、埋点重复上报、微前端重复挂载等问题。

请设计一套面向大型 Vue 3 应用的 **BFCache（Back/Forward Cache）生命周期与资源治理架构**。要求既尽可能提高 BFCache 命中率，又保证页面被冻结、恢复、重新加载等不同生命周期路径下的状态一致性、资源安全和可观测性。你需要说明哪些资源可以跨冻结保留、哪些必须暂停或重建，以及如何避免业务组件各自监听浏览器事件形成不可治理的生命周期逻辑。

## 背景 / 场景

系统存在以下约束：

- 页面常驻时间可能超过 8 小时，期间权限、Feature Flag、用户组织信息可能变化。
- 页面存在 WebSocket/SSE、定时轮询、Web Worker、BroadcastChannel 与第三方监控 SDK。
- 多个微前端独立开发，但共享宿主生命周期。
- Vue 3 页面内部大量使用 `onMounted` / `onUnmounted` 管理资源。
- 用户反馈“后退回来页面很快，但数据偶尔是旧的”；监控却把 BFCache 恢复误判成普通页面加载。
- 业务要求优先保留表单、滚动位置和昂贵的 UI 状态，同时不能因为恢复旧快照造成越权展示或重复副作用。

## 核心考察点

- 能否区分 SPA 路由生命周期、Document 生命周期与 BFCache freeze/restore 语义，而不是把 `onMounted/onUnmounted` 当成唯一生命周期。
- `pagehide` / `pageshow`、`event.persisted`、`visibilitychange` 等信号的职责边界，以及为什么不应依赖 `unload` 作为核心清理机制。
- BFCache Eligibility 与业务资源治理之间的关系：不能为了“清理干净”反而主动破坏可缓存性。
- 将副作用从组件中抽离为统一 Resource/Lifecycle Manager：连接、Timer、Worker、订阅、锁、Telemetry 等资源具有显式 acquire / suspend / resume / dispose 生命周期。
- 恢复后的 Freshness Validation：权限、Token、Feature Flag、关键 Server State 不能默认信任冻结前快照。
- Pinia 中 UI State 与 Server-authoritative State 的分层；哪些状态可直接恢复，哪些必须 revalidate。
- 多微前端环境下宿主发布统一 lifecycle contract，子应用不得直接竞争全局浏览器生命周期。
- 幂等恢复：重复 `pageshow`、连接重试、路由恢复等路径不能产生重复订阅和重复副作用。
- BFCache 恢复的性能与可靠性可观测：命中率、恢复耗时、revalidation 耗时、重复资源数、恢复后错误率。

## 追问方向

1. `onUnmounted` 为什么不足以处理 BFCache？页面进入 BFCache 时 Vue 应用一定会卸载吗？
2. 如果 WebSocket 导致某些浏览器下页面无法进入 BFCache，你会选择保持连接、主动关闭还是在 `pagehide` 中 suspend？决策依据是什么？
3. BFCache 恢复后，Pinia 中有一个 30 分钟前取得的 `canDeleteUser=true`。UI 是否可以立即显示删除按钮？如何避免安全问题与明显闪烁之间的冲突？
4. 一个页面恢复时同时有 20 个 Store 请求 revalidate，如何避免恢复瞬间形成 request storm？
5. 微前端 A、B 都注册了 `pageshow` 并恢复自己的 WebSocket，如何从平台层治理？
6. 如何区分 cold navigation、reload、SPA navigation 与 BFCache restore，并把它们纳入同一套前端 Trace？
7. 如果恢复过程中网络离线，你如何定义 UI State、Server State 和权限状态的降级策略？
8. BFCache 命中率突然从 70% 降到 15%，如何快速判断是新 SDK、事件监听器、响应头还是业务资源导致？

## 参考答案要点

### 1. 先建立三层生命周期模型

候选人应明确区分：

- **Document Lifecycle**：Document 创建、隐藏、进入历史记录、可能被冻结、恢复或真正销毁。
- **Application Lifecycle**：Vue App / 微前端实例的 bootstrap、active、suspended、disposed。
- **Route/Component Lifecycle**：Vue Router 与组件的 mounted、activated、deactivated、unmounted。

BFCache 恢复通常不是“重新启动 Vue 应用”。如果架构只把资源创建放在 `onMounted`、销毁放在 `onUnmounted`，就无法正确表达 suspend/resume。

### 2. 建立统一 Lifecycle Coordinator

宿主应用集中监听浏览器生命周期，再转换成稳定的内部协议，例如：

```tsx
type AppLifecycle =
  | { type: 'active'; reason: 'initial' | 'restore' }
  | { type: 'hidden' }
  | { type: 'suspend'; reason: 'history' }
  | { type: 'resume'; persisted: boolean }
  | { type: 'dispose' }
```

业务组件和微前端订阅平台协议，而不是任意注册全局 `pageshow/pagehide`。这样才能统一顺序、错误隔离、超时、指标和版本演进。

### 3. Resource Manager 应管理副作用，而不是管理页面数据

资源应有显式生命周期，例如：

```tsx
interface ManagedResource {
  suspend(): Promise<void> | void
  resume(): Promise<void> | void
  dispose(): Promise<void> | void
}
```

资源注册必须带稳定 identity，保证 acquire/resume 幂等。连接类资源可在 suspend 时停止网络活动，在 resume 时根据策略重新连接；Timer 停止并记录语义 deadline，而不是简单记住剩余 `setTimeout`；Worker 根据成本决定暂停协议或重建；Telemetry 必须避免恢复时重复初始化 session listener。

### 4. 状态必须按权威性分层

建议至少拆为：

- **Ephemeral UI State**：展开项、输入草稿、滚动位置，可直接保留。
- **Derived State**：可由可信状态重新计算，不需要网络刷新。
- **Cached Server State**：允许 stale-while-revalidate，但必须带 `fetchedAt/version/etag`。
- **Security-sensitive State**：权限、租户、身份、关键 Feature Policy，恢复后必须快速重新验证，不能把冻结快照作为授权事实。

前端即使暂时显示旧 UI，真正的敏感操作仍必须由服务端重新授权。对于高风险 capability，可以在 revalidation 完成前进入 `unknown/pending`，而不是继续使用旧 `true`。

### 5. 恢复不是全量刷新，而是一次有预算的 Reconciliation

恢复时建立 `RestoreTransaction`，收集需要验证的 domain，而不是让 20 个 Store 自行请求。调度器按 criticality、staleness、dependency、visibility 合并请求，并设置 concurrency budget。

关键路径可以是：Identity → Tenant/Permission → Feature Policy → 当前视图关键数据；低优先级数据延迟到 idle 或真正可见时刷新。

### 6. 所有恢复逻辑必须幂等

WebSocket 使用 connection identity / generation；订阅使用 stable subscription key；请求使用 request generation 或 AbortController；微前端 mount 使用 instance identity。旧 generation 返回的数据不得覆盖新 generation 状态。

因此 `resume()` 的语义不是“再执行一次初始化”，而是把资源收敛到目标状态。

### 7. 微前端使用 Capability + Lifecycle Contract

Shell 是 Document Lifecycle 的唯一协调者。子应用声明自己需要的资源能力，例如 network-stream、worker、polling，并实现 suspend/resume hook。Shell 控制调用顺序、timeout 和 fault isolation。某个子应用恢复失败不应阻塞整个页面恢复。

### 8. 可观测性要把 BFCache 当成独立导航类型

Navigation/Trace 至少区分：`cold-load`、`reload`、`spa-navigation`、`bfcache-restore`。建议记录：BFCache eligible/restore ratio、restore-to-interactive、critical revalidation latency、resource resume failures、duplicate connection/subscription count，以及恢复后短窗口内的 error rate。

恢复 Trace 应继续表达用户的一次 navigation，但不能错误复用冻结前已经结束的 performance span。

### 9. 典型故障治理

- **重复 WebSocket**：连接 generation + Resource Registry + 单例 ownership。
- **旧权限**：security state 标记 stale，恢复后优先验证，服务端始终强制授权。
- **请求洪峰**：Restore Scheduler + request dedup + priority/concurrency budget。
- **微前端重复挂载**：instance identity + 幂等 activate/resume。
- **埋点重复**：SDK 初始化与 navigation event 分离；restore 产生新的 navigation observation，而不是重新 bootstrap SDK。
- **BFCache 命中率下降**：建立 eligibility telemetry，并按 release、browser、route、第三方 SDK 版本做关联分析。

## 架构师级判断标准

优秀候选人不应把问题回答成“监听 `pageshow` 后重新请求接口”。关键是建立 **Document Lifecycle → Lifecycle Coordinator → Resource Manager → Restore Scheduler → Domain Reconciliation → Vue State Projection** 的分层模型。

真正需要治理的是两个目标之间的张力：**尽量保存昂贵且安全的客户端状态以获得瞬时恢复，同时把网络连接、服务端事实和安全敏感状态视为需要重新协调的外部世界。** BFCache 是浏览器提供的性能能力，但大型应用必须额外补齐生命周期协议、幂等资源管理、状态权威边界和恢复可观测性，才能把它安全地用于生产环境。
