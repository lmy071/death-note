# 2026-09-13｜前端构建产物缓存一致性治理

## 题目

你负责一个拥有 200+ 前端包、30+ Vue 3 应用的 Monorepo。团队已经建立 CI 构建缓存、远程缓存、CDN 静态资源缓存和 Service Worker 缓存，但近期连续出现以下问题：

- 某次只修改一个基础工具包，却触发大量应用重新构建，CI 从 12 分钟增长到 45 分钟；
- 另一次构建缓存错误命中，应用发布后出现新 HTML 引用了旧 JS Chunk，部分用户白屏；
- 多个应用共享同一个内部 SDK，但不同流水线偶尔产出内容不同、文件名相同的 Artifact；
- 紧急回滚后，部分用户仍然命中 Service Worker/CDN 中的新版本资源，导致前后端协议不兼容；
- 团队准备引入更激进的 Remote Cache 和增量构建，但担心进一步扩大错误缓存的爆炸半径。

请你从前端架构师视角设计一套 **Build Artifact + Cache Consistency Architecture**。要求既提高大型 Monorepo 的构建吞吐，又保证“缓存命中一定等价于重新构建”的正确性，并设计发布、回滚、缓存失效和可观测性机制。

## 背景 / 场景

技术栈为 Vue 3 + TypeScript，使用 Monorepo 管理多个业务应用和共享 Package。CI 中包含 Type Check、Lint、Unit Test、Bundle Build、SSR Build 等任务，并存在本地缓存、CI Remote Cache、对象存储、CDN、浏览器 HTTP Cache 与 Service Worker 多级缓存。

系统要求：开发者提交代码后，大部分未受影响应用能够跳过构建；任意缓存节点出现错误都不能静默污染生产；构建结果应具备可复现性；支持秒级回滚且不能依赖“等待 CDN 缓存自然过期”；可以回答某个生产 JS 文件究竟由哪个 Commit、依赖图、构建器版本和 CI Task 产生。

## 核心考察点

1. **任务图与影响分析**：能否区分 Source Dependency Graph、Task Graph 与 Runtime Dependency Graph，并根据输入闭包计算 affected tasks，而不是简单按 Git diff 决定是否构建。
2. **Cache Key 设计**：是否理解 Cache Key 必须覆盖源码、锁文件、环境变量、编译器/插件版本、构建配置、Node Runtime、目标平台等所有会影响输出的输入。
3. **Hermetic / Reproducible Build**：是否能识别时间戳、随机数、绝对路径、网络请求、未声明环境变量等非确定性输入对远程缓存正确性的破坏。
4. **Content-addressed Artifact**：是否采用内容哈希标识 Artifact，并区分逻辑版本、发布版本与不可变构建产物。
5. **缓存信任边界**：Remote Cache 不应只是一个 key-value 下载服务，需要考虑写权限、命名空间、完整性校验、缓存投毒以及 PR 与主干之间的隔离。
6. **多级缓存一致性**：CI Cache、Artifact Store、CDN、HTTP Cache、Service Worker 的失效策略应分层设计，而不是使用统一 TTL。
7. **原子发布与回滚**：是否采用 Immutable Asset + Version Manifest/Release Pointer，使发布本质上成为原子切换，而不是覆盖已有文件。
8. **可观测性与治理**：Cache Hit Ratio 只是效率指标，还需要 Cache Correctness、Build Critical Path、Invalidation Fan-out、Artifact Provenance 等指标。

## 追问方向

1. `src/a.ts` 没变化，但它依赖的 TypeScript Compiler 从版本 N 升级到 N+1，Remote Cache 是否应该命中？为什么？
2. 如果某个构建插件偷偷读取 `process.env.REGION`，但 REGION 没进入 Cache Key，会发生什么？如何自动发现这类 undeclared input？
3. 为什么 `app.js?v=123` 通常不如 `/assets/app.<content-hash>.js` 适合作为不可变 Artifact？
4. HTML 应该使用 `Cache-Control: no-cache` 还是长时间 immutable？JS/CSS 呢？为什么两者策略不同？
5. Service Worker 在用户长时间不关闭 Tab 时如何安全升级？如何避免新旧 Chunk 与 API Schema 混用？
6. 如果 Remote Cache 中已经存在一个错误 Artifact，如何防止它继续污染后续 100 个 Pipeline？
7. 如何证明同一 Commit 在两台 CI Runner 上产生完全一致的构建结果？如果不一致，你会如何定位？
8. Monorepo 中一个公共 Package 修改后导致 80% 应用 invalidation，你如何判断这是合理依赖传播还是架构耦合问题？
9. 发布已经切换到 v42，随后发现严重问题。如何做到回滚到 v41 时不重新构建？
10. 如果 CDN 支持 purge，为什么仍然应该优先设计 Immutable Asset，而不是依赖 purge 保证一致性？

## 参考答案要点

### 1. 建立三层模型，而不是把“构建缓存”当成单一功能

建议把体系拆成 **Build Graph、Artifact Store、Release Control Plane**。

Build Graph 负责回答“哪些 Task 必须重新执行”；Artifact Store 负责回答“某个输入闭包对应的可信输出是否已经存在”；Release Control Plane 负责回答“当前生产环境应该引用哪组 Artifact”。三者不能混为一谈。

### 2. Cache Key 应表示完整输入闭包

可以抽象为：

```
TaskKey = Hash(
  source inputs
  + dependency task outputs
  + lockfile
  + build config
  + compiler/plugin versions
  + declared environment
  + runtime/toolchain version
  + target platform
)
```

关键不是 Hash 算法本身，而是 **Input Completeness**。只要遗漏任何会改变输出的输入，就可能产生 false hit；包含大量实际上不会影响输出的输入，则会产生 false miss，降低缓存收益。

因此架构目标是在 Correctness 和 Cache Granularity 之间寻找平衡，而不是单纯追求 Hit Ratio。

### 3. 构建任务必须尽可能 Hermetic

Task 应显式声明 inputs / outputs，限制任意网络访问、系统时间、随机值、机器路径和隐式环境变量。

可以通过 Sandbox、文件访问审计、环境变量白名单和双构建一致性检查发现 undeclared input。对于无法做到 Hermetic 的 Task，应明确标记为 non-cacheable，而不是强行进入 Remote Cache。

### 4. Artifact 与 Release 解耦

构建产物使用 Content Hash：

```
/assets/app.a81f92.js
/assets/vendor.29cd10.js
```

这些 Artifact 一旦上传即不可修改，并设置长 TTL + immutable。

发布系统额外生成 Release Manifest：

```
release-v42 -> {
  indexHtml,
  jsChunks,
  cssChunks,
  apiContractVersion,
  buildProvenance
}
```

生产入口只需要原子地把 active release 从 v41 切换到 v42。回滚就是把 Pointer 指回 v41，因此不需要重新构建，也不需要覆盖旧文件。

### 5. HTML 与静态 Artifact 使用不同缓存策略

带 Content Hash 的 JS/CSS 可以永久缓存，因为内容改变意味着 URL 改变。

HTML / Release Manifest 则承担版本发现职责，需要短缓存或 revalidation。核心原则是：**可变资源负责发现版本，不可变资源负责承载版本。**

### 6. Service Worker 必须进入 Release Protocol

SW 不应独立决定资源版本，而应绑定 Release ID。Cache Storage 可以按 `app:v41`、`app:v42` 建立 namespace。

升级时先下载并验证新版本完整资源，再原子激活；旧页面继续使用旧 namespace，新导航进入新版本。不能在同一个运行中的页面里逐个替换 Chunk，否则容易形成 mixed-version runtime。

必要时可以通过 BroadcastChannel 通知用户刷新，但是否强制刷新应根据业务风险决定。

### 7. Remote Cache 是供应链的一部分

PR Pipeline 不应拥有覆盖主干可信 Cache Namespace 的权限。缓存对象应进行 digest 校验，并记录 producer commit、task key、toolchain、runner identity、时间和签名/attestation。

发现错误缓存后，应支持按 TaskKey、Toolchain Version 或 Namespace 进行 quarantine，而不是只删除单个文件。

### 8. 建立 Artifact Provenance

每个生产 Artifact 应能够追溯：

```
Artifact Digest
  -> Task Key
  -> Source Commit
  -> Dependency Digests
  -> Lockfile Digest
  -> Toolchain Image
  -> CI Run
  -> Release ID
```

这样线上错误才能从“某个 JS 报错”反查到具体构建环境，而不是依赖人工猜测。

### 9. 监控重点不是只有 Cache Hit Ratio

建议至少关注：

- Cache hit / miss / false-hit 检测结果；
- 每类 Task 的 P50/P95 构建耗时；
- Critical Path Length；
- Invalidation Fan-out；
- Remote Cache 下载时间与重新计算成本的比较；
- Artifact Reproducibility Failure；
- Release Manifest 与 Artifact 完整性异常；
- CDN/SW Mixed-version 事件。

如果一个 200ms Task 从 Remote Cache 下载需要 800ms，就算“命中”也不一定值得缓存，因此 Scheduler 应允许按 Task Cost 决定缓存策略。

### 10. 架构层面的最终判断

优秀答案不应停留在 Turborepo、Nx、Vite 或某个 CI 产品的配置，而应建立一条完整的不变量：

> **相同的声明输入必须产生相同输出；不同输出必须拥有不同 Artifact Identity；已经发布的 Artifact 永不修改；Release 只引用一组经过验证的不可变 Artifact。**
> 

在此基础上，Remote Cache 才是性能优化，而不是正确性的来源。缓存失效可以导致性能下降，但不能导致系统返回错误版本。
