# 2026-09-05｜微前端跨应用依赖治理

## 题目

你负责一个拥有 20+ 业务团队的大型 Vue 3 平台，采用微前端架构。各子应用独立开发、构建和发布，但逐渐出现以下问题：同一页面同时加载多个 Vue、Pinia、组件库和监控 SDK 版本；公共依赖升级困难；某个子应用升级共享依赖后导致其他应用运行时异常；首屏 JS 体积持续增长；不同子应用之间存在隐式全局变量、CSS 和运行时副作用。

请你设计一套**微前端跨应用依赖治理体系**。要求既保持团队独立发布能力，又控制重复依赖、版本漂移、运行时冲突和故障爆炸半径。请说明你如何划分共享依赖与私有依赖，以及如何设计构建期、发布期和运行时三层治理机制。

## 背景 / 场景

公司正在把一个大型 Vue 3 管理平台拆分为多个业务子应用。当前通过 Module Federation / 动态加载机制组合应用，主应用负责导航、认证和基础设施。

随着团队数量增加，出现以下约束：

- 不允许所有团队被迫同步升级，否则微前端失去独立发布价值。
- Vue 3、Pinia、设计系统、国际化 SDK、监控 SDK 等部分依赖希望复用。
- 子应用可能同时存在多个历史版本，需要渐进迁移。
- 某些依赖要求单例运行，而另一些依赖允许多版本共存。
- CDN 缓存、动态 chunk 和远程模块存在版本不一致风险。
- 平台要求单个子应用故障不能拖垮整个页面。

## 核心考察点

- **依赖所有权模型**：能否区分 Platform Dependency、Shared Runtime、Application Private Dependency，而不是简单地把所有公共包都 externalize。
- **Singleton 判断能力**：理解 Vue runtime、全局状态容器、Router、SDK 等依赖为何可能要求单实例，以及错误共享的风险。
- **版本兼容协议**：SemVer 只是版本描述，不能替代真正的运行时兼容性契约；需要考虑 capability / protocol version。
- **构建体系治理**：Module Federation shared 配置、lockfile、依赖图分析、bundle duplication detection、CI policy。
- **发布一致性**：Remote Manifest、immutable artifact、版本固定、CDN 缓存策略以及避免 HTML / remoteEntry / chunk 混合版本。
- **运行时隔离**：JS Realm、CSS Scope、全局副作用、错误边界以及单个 remote 加载失败后的降级。
- **渐进升级能力**：如何实现 N / N+1 双版本窗口，而不是一次性全量迁移。
- **可观测性**：能够回答线上到底加载了哪个 host、remote、shared dependency 和 artifact hash。

## 追问方向

1. Vue 3 是否一定应该配置成全局 singleton？什么情况下你反而允许两个 Vue runtime 共存？
2. 如果 A 应用要求组件库 `^4`，B 应用要求 `^5`，你如何处理？是否应该由 Module Federation 自动选择一个版本？
3. 为什么“所有公共依赖都放到主应用”最终可能形成新的前端单体？
4. remoteEntry 已更新，但用户缓存了旧 chunk，如何避免 `ChunkLoadError` 或 ABI 不兼容？
5. 某个 shared SDK 新版本存在内存泄漏，但已经被 15 个子应用引用，如何做到快速止血？
6. 如何自动发现同一个页面加载了 3 份 lodash、2 份 Vue 或多个埋点 SDK？
7. 如果团队希望独立升级 Vue 3 minor 版本，你会如何定义兼容窗口和退出机制？
8. 微前端之间应该直接共享 Pinia Store 吗？如果不共享，跨应用状态如何通信？

## 参考答案要点

### 1. 先建立依赖分层，而不是从打包配置开始

建议至少划分三层：

**Platform Runtime**：生命周期由平台控制，例如微前端 orchestrator、认证桥接、全局 telemetry、跨应用事件协议。此层 API 必须非常稳定。

**Shared Dependency**：只有满足“体积收益明显 + 版本兼容稳定 + 多实例存在明确成本”的依赖才进入共享池。Vue runtime 是否进入此层需要结合隔离模型决定，而不是默认共享。

**Application Private Dependency**：业务库、变化频繁的工具库以及存在版本耦合风险的依赖优先由子应用自行打包。允许一定程度的重复代码，以换取部署独立性和故障隔离。

架构目标不是实现零重复依赖，而是在 **bundle size、自治性、兼容性和 blast radius** 之间取得可控平衡。

### 2. 不把 SemVer 当成运行时兼容协议

`^x.y.z` 只能表达包管理器层面的版本范围。对于真正跨应用的 runtime API，应建立显式协议版本，例如：

```tsx
interface RuntimeCapabilities {
  protocolVersion: 3
  capabilities: Array<'auth-v2' | 'telemetry-v3' | 'navigation-v2'>
}
```

Remote 在启动前执行 capability negotiation；缺少必要能力时拒绝挂载或进入降级模式，而不是等运行过程中出现 undefined function。

### 3. 对 Singleton 做严格准入

Singleton 应是例外，而不是默认策略。

适合考虑 singleton 的依赖通常具有全局身份或上下文语义，例如共享同一个 Vue App Context 的场景、统一 telemetry runtime 或某些全局 SDK。

普通工具库即使重复几十 KB，也可能比强制全局单版本更加安全。

如果不同子应用拥有严格隔离的 DOM / runtime 边界，允许多个 Vue runtime 有时反而可以降低升级耦合；代价是额外 bundle 和内存开销。

### 4. 构建期建立 Dependency Policy Engine

CI 应生成完整 dependency graph，并自动检测：

- 禁止依赖版本。
- singleton 版本冲突。
- 同页面高成本重复依赖。
- shared dependency 的 breaking upgrade。
- bundle size regression。
- 未授权的全局副作用依赖。

策略应该支持 warning → blocking 的渐进治理，而不是一次性强制所有仓库升级。

### 5. 发布采用 Manifest + Immutable Artifact

每次部署生成不可变 artifact，例如：

```
app-a@2.8.1
remoteEntry.8fa21.js
chunk-a.92bc1.js
```

Host 不直接依赖“latest remoteEntry”，而通过 Release Manifest 解析明确版本：

```
page-release-1042
 ├─ shell@7.2.0
 ├─ app-a@2.8.1
 └─ app-b@5.4.3
```

这样可以保证一次页面会话中的应用版本集合可复现，并允许 Manifest 级原子回滚。

### 6. 允许有限的 N / N+1 共存窗口

大型组织无法要求所有子应用同时升级共享 runtime。

可以规定平台只维护当前版本 N 与上一版本 N-1，通过 adapter / compatibility layer 兼容；超过窗口的应用进入迁移阻断状态。

这比“永远向后兼容”更可持续，因为后者会让平台层不断累积历史债务。

### 7. 跨应用状态优先共享协议，不共享实现

不建议让多个微前端直接读写同一个 Pinia Store。这样会把 Store schema 变成隐式分布式 API，并产生部署时序耦合。

更合理的是通过 typed event / command / query contract 交换领域信息，例如：

```
UserChanged
WorkspaceSelected
PermissionUpdated
```

每个子应用维护自己的状态投影。跨应用真正需要强一致的数据，应由后端或平台级 domain service 提供权威状态。

### 8. 运行时必须具备隔离和降级能力

Remote 加载需要 timeout、retry、circuit breaker 和 fallback UI。Vue 层通过 Error Boundary / `errorCaptured` 控制组件故障域；CSS 使用 scoped namespace、CSS Modules 或 Shadow DOM 等机制减少污染。

任何 remote 初始化失败都不应该阻塞 shell 与其他业务应用启动。

### 9. 建立微前端 Runtime Inventory

每次页面启动记录：

```
shellVersion
remoteName / remoteVersion
artifactHash
sharedDependencyVersions
protocolVersion
releaseId
```

这些信息进入统一 telemetry，并与错误、Web Vitals、Long Task 和用户会话关联。

出现线上故障时，必须能够回答：**哪个用户、在哪个 release、加载了哪组 remote 和 shared runtime 版本后发生了问题。**

## 架构师级回答的关键判断

优秀答案通常不会追求“所有依赖只加载一次”，而会明确指出：**微前端依赖治理的核心不是最大化共享，而是管理跨独立部署单元之间的运行时耦合。**

真正需要优化的是三个指标：**升级协调成本、运行时冲突概率、故障爆炸半径**。Bundle 重复率只是其中一个工程指标，不能凌驾于部署自治和系统可靠性之上。
